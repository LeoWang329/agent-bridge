## 这份文档要回答什么

你看到一篇讲 Claude Code「动态工作流（Dynamic Workflows）」的调研文章，社区里有人给它起了个别名叫「Graph Engineering（图工程）」。你问两件事：

1. 我们这个 agent-bridge 项目，适不适合做这种东西？
2. 如果做，应该怎么做成项目里的一个「技能（skill）」？

这份文档就是答案。先把这套东西讲清楚（用大白话），再说清楚适不适合、以及讨论收敛出的具体做法。

---

## 一句话结论

**适合做，而且该做。但要分清两件事：不造流程引擎（那种引擎 Claude Code 已经自带），却要支持"临时写一段 JS 来编排流程"——后者正是调研说的动态工作流本来的样子，而且节点可以是不同引擎的 AI，这是 Claude 自带的做不到的。**

**第一版交付三样东西**：一个"叫一个 AI 干一件事"的命令、一个"几个 AI 分头干再等齐"的命令、以及一个**可以被 JS 脚本 `import` 的内核**——让你为具体任务临时写几十行编排代码。通用的图引擎（plan 格式、DAG 解析、调度器）一概不做。

---

## 第一部分：这套东西到底是什么（不绕圈子）

### 1. 核心思想：把活分成两种

一个多 AI 协作的任务，其实是两种活混在一起：

- **一种活是"死板但要绝对可靠"的**：比如"把这 20 个文件挨个检查一遍""等三个 AI 都回复了再往下走""如果没查出问题就停"。这种活是**流程调度**，不需要动脑子，但一步都不能错、不能忘。
- **另一种活是"需要动脑子、要理解和判断"的**：比如"读懂这段代码有没有安全漏洞""比较两个设计方案哪个更好""写一段修复代码"。这种活才是真正需要 AI 的地方。

动态工作流的做法是：**把第一种活写成一段普通的程序代码（可靠、不会忘、不会累），把第二种活交给 AI 去干。**

打个比方：这就像一条流水线。传送带的节拍、质检卡口，是**写死的流程**（程序）；每个工位上真正干活的**是工人**（AI）。你不会让工人去记整条流水线的节拍，那样容易乱；节拍交给机器，工人只管自己那道工序。

### 2. 为什么这被叫做"图（graph）"

因为这种流程天然长得像一张图：每叫一次 AI 干一件事 = 一个**点**；把一个 AI 的结果传给下一个 AI = 一条**线**；让五个 AI 同时干 = **分叉**；等五个都干完再汇总 = **汇聚**；"没查完就再来一轮" = 一个带停止条件的**环**。

所以"graph 工程"里的"图"，指的是**任务的流程图**，不是知识图谱、也不是数据库那种图。

### 3. 这套东西擅长什么

调研文章列了 6 种典型玩法，翻译成人话：

| 玩法 | 人话解释 |
|---|---|
| **分头查、再汇总** | 一个大代码库要审计，拆成 20 块让 20 个 AI 同时查，最后汇总 |
| **一个干、一个挑刺** | 一个 AI 出结果，另一个独立的 AI 专门反过来找毛病（适合"错了代价很大"的场景） |
| **多个抢答、选最好** | 同一个问题让好几个 AI 各自独立解，再比一比、选出最好的 |
| **先分类、再分流** | 先让一个 AI 判断"这属于哪类问题"，再按类别送到对应的处理环节 |
| **多生成、再筛选** | 让好几个 AI 各出一批候选，再去重、过滤、排序 |
| **反复干到好为止** | 查—修—再查，直到查不出新问题为止 |

前三种有个共同点：**多个 AI 之间的"不一样"本身就是价值**——挑刺、抢答，越是来自不同的"脑子"，结果越可靠。后三种就不一定。**这个区别是后面选型的关键**，第六部分会给一张完整的对照表：什么场景走哪种玩法、用我们的工具具体怎么走、哪几种其实用不上我们。

## 第二部分：一个绕不开的事实——Claude Code 已经自带了这个

这一点直接决定我们"该不该自己造"。

**Claude Code 本身已经内置了动态工作流的能力**（主 agent 手上有个叫 `Workflow` 的工具）。按调研文章的说法，它已经能：把活拆开并行跑（一次最多同时跑 16 个）、一次运行最多起一千个环节、跑的过程能在 `/workflows` 界面里看到。

它也有两个明确的局限，调研里写得很清楚：

- **中途暂停只能在同一个 Claude Code 会话里接着跑；退出之后再跑是从头开始**，不能跨会话恢复。（这一条对我们反而**有利**，后面第五部分的"回执落盘"正好比它强。）
- **它每个环节叫的 AI，本质上还是 Claude**。（调研没有直说这一句，但 Claude Code 的子 agent 就是 Claude；想跳出去只能靠子 agent 自己去命令行里叫别人。）如果想在某个环节用 codex 或 kimi，只能绕一大圈——先起一个 Claude，让这个 Claude 再去转手叫 codex。等于每个环节都多垫了一层 Claude，又费又绕。

**所以真正的问题不是"我们能不能造一个流程引擎"，而是——既然人家已经有一个成熟的引擎，我们这个技能到底该做什么才有意义？**

## 第三部分：agent-bridge 适不适合——分两层看

沿用第一部分那两层来看：

### AI 干活这一层：agent-bridge 非常适合，而且比 Claude 自带的强

agent-bridge 本来就是干这个的——能同时接通**五个不同的 AI 后端**：OMP、Codex、Claude、Cursor、Kimi（其中 OMP 本身还是个路由器，能再转接 deepseek 等多家模型）。

前面说过，"多个 AI 之间的不一样本身就是价值"。在这一点上，agent-bridge 不是比 Claude 自带的好一点点，而是**做到了它做不到的事**：让 codex 去挑 kimi 的刺、让三个不同引擎的 AI 抢答同一道题。这种"真·不同脑子"的独立性，只有 Claude 一家的工作流给不了。

**这一层，就是 agent-bridge 独一无二的价值。**

### 流程调度这一层：现在是空白，但项目早就打算往这走

agent-bridge 现在怎么调度？靠**主 agent 自己按一份文字手册（skill）一步步手动操作**。也就是说，"什么时候叫谁、等谁、传什么"这些流程，现在装在主 agent 的脑子里、靠自觉执行。

毛病是：流程越复杂，主 agent 的上下文就被这些琐碎调度占得越满，越容易出错、越容易忘。而动态工作流的核心好处，恰恰是**把这些调度从主 agent 脑子里搬出来、变成可靠的程序代码**。

好消息是：**项目自己早就写下过要往这个方向走。** 内部有一份讲"编排从文字手册演化到代码"的文档，明确说过终点是"代码负责流程骨架、AI 只在需要判断的地方出手"。动态工作流几乎就是这份路线图的通用版终点。

### 小结：定位要摆正

agent-bridge 适合做，但**不是去重造流程引擎**（那会造出一个比 Claude 自带的还弱的东西），而是**补上 Claude 自带工作流缺的那块——让不同引擎的 AI 能作为环节协作**。

**那"流程"这一层交给谁？** 调研文章的核心正是这一句：**Claude 临时写一段 JavaScript 编排脚本，由一个 runtime 执行**。所以这个问题必须正面回答。有三条路：

- **路 A（最省事，适合简单情况）**：**主 agent 自己按顺序敲命令**——先跑一条"分头干"，看看结果，再跑一条"汇总"。不需要写任何代码。好处是今天就能用；坏处是流程还在主 agent 脑子里，只适合两三步的简单组合。
- **路 B（这才是调研说的那种玩法，第一版必须支持）**：**为这一次任务临时写一个几十行的 JS 脚本**，循环、分支、过滤全用普通的 JS 写，中间结果存在变量里，主 agent 只收最后一个结果。**这条路对我们几乎是免费的**——只要把工具的内核（`node-core.mjs`）写成能被 `import` 的模块就行，具体见第五部分"写法三"。
- **路 C（不通，别指望）**：让 Claude Code 自带的 Workflow 脚本来调用我们的工具。**走不通**：调研文章第 129 行写明，那种脚本跑在隔离环境里、**不能跑命令**，所以它没法直接调我们的命令行工具。硬要接只能让它先起一个 Claude 子 agent、再由子 agent 去命令行里调——每个环节多垫一层 Claude，又费又绕。

**这里有个容易搞混的地方，得说清楚**：路 B 的那段 JS **跑在普通的 node 里（我们自己起的进程）**，不是跑在 Claude Code 的 Workflow runtime 里。所以那条"runtime 不能跑命令"的限制**对我们不成立**——**这反而是我们比原生灵活的地方**：我们的编排脚本想跑什么命令、想读什么文件都行。

**所以这个定位的准确说法是：我们不造流程引擎，但我们支持"临时写一段 JS 来编排流程"——这正是调研说的动态工作流本来的样子。** 需要写死的通用引擎（plan 格式、DAG 解析、调度器）一概不做；需要判断的流程，每次现写现扔。

## 第四部分：三个 AI 一起讨论，吵出了什么

我把背景整理成简报交给 codex 和 kimi，各自独立作答，再互相看对方的答案、互相挑刺，收敛了三轮。之后又请了一个独立的复核 agent 核对全文。几件值得记下来的事：

### 关于"怎么写调度代码"的一个前提

两个 AI 都去翻了源码，各自确认：`scripts/agent-bridge.mjs` 是一整块、**没有对外开放任何可复用的函数接口**（5491 行，跑到最后直接进命令行入口）。所以路线图文档里说的"以后写调度代码可以直接复用桥的内部机制"，**今天还做不到**——今天只能让工具**自己另起一个 agent-bridge 后台进程、通过标准输入输出对话**。

**这个结论不新**：仓库里 `docs/repro-mcp-hang/` 下的 **49 个脚本一直是这么干的**，还带着 **五个假后端**（fake-omp / fake-codex / fake-claude / fake-cursor / fake-kimi）。好处是——**那份最小 MCP 客户端代码可以直接抄，不用从零写**（`repro-waitany.mjs` 里 spawn + 握手 + 调用工具那几十行）。

### 两个想法在讨论中被否掉了（包括我自己提的）

- **我提过一个"省进程"的主意**：让多次独立的工具调用共用同一个常驻的 agent-bridge 后台进程。**被两个 AI 各自核实后否掉了**：桥的会话活在"谁起的谁独占"的那个进程里，客户端一退出会话全清，而且它只认标准输入输出、不是那种能被很多人同时连的网络服务。想做"常驻共享"，得先给桥加一层它现在没有的东西，还会带出"谁负责关它、谁的活谁清理"的烂账。不划算。
- **codex 一度主张"自动往下走"**：等所有并行环节都成功了，程序**自动**去启动下一步（比如自动叫一个 AI 来汇总）。**被 kimi 用项目自己的例子驳倒了**——项目里现有的技能，对"一个环节的 AI 挂了"这件事，处置方式**各不相同，而且没有一个是"全停"**：

  | 技能 | 一个环节的 AI 挂了，怎么办 | 出处 |
  |---|---|---|
  | 圆桌（roundtable） | 当作掉线席、**带着缺口继续综合**；只有活着的独立席少于 2 席才停下问人 | `agent-bridge-roundtable/SKILL.md:178` |
  | 循环（loop） | **换一个引擎把这个环节重开一次**（交接物都在文件里，重开不亏） | `agent-bridge-loop/SKILL.md:320` |

  两个技能对同一件事给出两种不同答案，恰恰说明"必须全部成功才继续、否则一律停"**不是中立规则**——这条规则等于替所有场景选了第三种答案。codex 在第三轮认了这一点。

  **这个对比还带出一条硬要求**：三种策略里有一种是"重试这一个环节"，所以工具必须让调用方**能只重跑失败的那一个环节**——汇总清单要逐环节给足信息（用的哪个 AI、哪一步失败、任务单原样），不能只给一个笼统的成功/失败。

## 第五部分：具体怎么做（第一版）

### 核心分寸：只把"最死板、最不会变"的那部分写成代码

用"等人吃饭"打比方最好懂：

- **"等所有人都到齐、并且清点确认每个人都来了" —— 写成代码。** 死板、可靠、跨场景都一样，不需要任何判断。
- **"等齐之后，去哪家饭店、点什么菜" —— 不写死，留给临场定。** 因为不同场景答案不一样（上面那张表已经证明：有的带缺口继续，有的换人重来），写死等于替所有场景做同一个决定。

**一句话：把"等待和清点"写进代码，把"等完之后干什么"留给临场判断。**

### 第一版交付什么

放在新目录 `skills/agent-bridge-graph/` 下。**主角是那个可被 `import` 的内核**，命令行入口只是给"懒得写脚本"的简单情况准备的薄壳：

| 交付物 | 是什么 | 分量 |
|---|---|---|
| **`tools/node-core.mjs`** | **可被 `import` 的内核**：起/关桥进程、跑一个环节的完整生命周期、落盘、校验、写回执 | **主角**——第六部分说的"写 JS 编排"全靠它 |
| `tools/node-turn.mjs` | 命令行：跑一个环节，不用写代码 | 配角（薄壳） |
| `examples/hetero-audit.mjs` | 可直接跑的示例：扇出 → 过滤 → 换引擎汇总 | 兼真跑 e2e |
| `SKILL.md` + `tools/README.md` | 说明书（150 行内）+ flag 级用法 | — |

生命周期那十来步**只在内核里实现一遍**，命令行是薄壳，以后改超时纪律只改一处，不会退回"抄三遍"的老问题。

> **`fan-run` 已砍掉（2026-07-25 拍板）**：原本还打算做个"几个环节同时跑、等齐、给汇总清单"的命令行。砍掉的理由是它**两头不靠**——能力是"写脚本"的**子集**（一份 JSON 任务单清单，说白了是一种更弱的编程语言：不能循环、不能分支、不能过滤），而"几个 AI 同时跑再等齐"光用桥本体也能做。比桥本体强的那点（结果不进主 agent 上下文），远不如直接写一行 `Promise.all` 来得彻底。
> **扇出交给脚本**（`await Promise.all(items.map(x => bridge.runNode(...)))` 一行的事）。等真发现"经常要扇出但又不想写脚本"，再补不迟。

**工具一：`node-turn.mjs`——"叫一个 AI 干一件事，从头到尾办完"**

给它一张"任务单"，它负责这一个环节的全过程，一步不落：开会话 → 发任务 → 等结果 → 存结果 → 检查格式 → 关会话 → 写回执。

关于"等"这一步，有两个容易踩的坑，工具必须替人管住：

- **超时是任务单的必填字段，工具保证每次等待都带上，不会漏**。内部按"短轮询循环"等——单次等待不超过 5 分钟、循环到总时长用尽。这样既不会死等，也不用为了怕超时把任务砍小。
- **一旦总时长用尽：先打断这一轮（`abort`），再关会话，最后才退出。** 因为桥的等待超时**本身不会打断任务**——任务还在后台继续烧。不主动打断就退出，会留下一个还在跑的后端进程。

为什么值得做成工具：现在这套固定动作，加上两条最容易出错的纪律（"等的时候一定要设超时""别用会卡死的等法"），已经被**一字不差抄进了三个不同的技能**。抄三遍，就说明该被抽成工具。做完之后，这个新技能会成为**第一个不用再手抄那两条纪律的技能**——**让那三处重复的抄写可以下架，这就是这个工具存在的意义**。

**写法二：`import node-core.mjs`——为这次任务临时写一段 JS 编排（这才是调研说的那种玩法）**

上面那个命令行够用于"就跑一个环节"。但**流程一复杂（要扇出、要循环、要按结果分支、要过滤），就该写一小段 JS**。做法是把内核 `node-core.mjs` 写成**能被 `import` 的模块**，然后为这一次任务临时写个几十行的脚本，用完就扔：

```js
import { withBridge } from "./node-core.mjs";

await withBridge(async (bridge) => {          // 一个桥进程，全程管到底
  const files = ["auth.ts", "api.ts", "db.ts"];

  const results = await Promise.all(          // 扇出：三家同时查
    files.map((f) =>
      bridge.runNode({ agent: "codex", prompt: `审计 ${f} 的权限校验`, /* … */ })));

  const bad = results.filter((r) => r.status !== "ok");   // 过滤：普通代码，不叫 AI
  if (bad.length > 1) return { halt: "挂太多，先查环境" }; // 分支：普通 if

  return bridge.runNode({                     // 汇总：换个引擎，别自己总结自己
    agent: "kimi",
    prompt: `读这几份结果并汇总：${results.map((r) => r.artifactPath).join(" ")}`,
  });
});
```

**为什么这条写法很重要**：它才真正兑现了 graph 工程的核心好处——**流程写在文件里、中间结果活在 JS 变量里、主 agent 只收最后一个结果**。前两种命令行写法只把"单个环节"做扎实了，流程还在主 agent 脑子里。

**为什么这条几乎不花额外成本**：内核本来就要写（两个命令行工具都靠它），只是多要求一条"**写成可以被 import 的模块**"而已。

**说清楚三件事，免得误解**：

1. **这不是"造引擎"。** 没有 plan 格式、没有 DAG 解析器、没有调度器。循环就是 `for`，分支就是 `if`，过滤就是 `filter`——**每次为当前任务现写现扔**（调研里管这叫"动态"，本来就是这个意思）。
2. **这段 JS 跑在普通 node 里**（我们自己起的进程），**不是**跑在 Claude Code 的 Workflow runtime 里。所以"runtime 不能跑命令"那条限制对它不成立。
3. **一个脚本全程只起一个桥进程**（`withBridge` 负责起和关），里面爱跑几个环节都行——不会因为并行就冒出一堆桥进程。

**内核要对外提供的东西**（第一版就这些，别多）：`withBridge(fn)`（起一个桥、用完关干净、异常也保证关）、`bridge.runNode(任务单)`（跑一个环节，返回回执）、`bridge.doctor()`（开跑前体检）。**不提供**任何"图""节点依赖""调度"的概念——那些用普通 JS 表达就够了。

**一份说明书：`SKILL.md`（150 行以内，尽量薄）**

写几样：什么时候该用（点名那 3–4 种"多个 AI 不一样才有价值"的玩法，**不做六种玩法平铺、显得都一样的流水账**）；两个工具怎么配合；五个后端的脾气差异（下面那张表）；一个完整例子。

### 一张"任务单"里要填什么

- **必填**：环节编号、用哪个 AI、在哪个目录干、干什么（一段话或一个文件）、超时多久、结果存哪。
- **选填**：用哪个具体型号、思考多深、角色设定文件、输出格式要求（见下条）、打回重说几次（默认 1 次，可设 0）。
- **并发上限**：脚本自己控制（一次 `Promise.all` 别超过 4 个）。**为什么是 4**：不是性能不够（实测三个后端并行只占 0.36 个核），而是桥的说明书里有条告警——**长请求碰上机器过载，客户端可能把整个 MCP 连接整个断掉**，而主 agent 自己的桥连接就在旁边跑着，不该去挤它。
- **结果存哪**：`outDir` 是**必填字段，由调用方自己给**（脚本自然要控制自己的产出目录）。约定俗成的写法是 `<工作目录>/.graph/run-<时间戳>/`，示例脚本就这么干。**工具不去动用户的 `.gitignore`**（那是替人改文件，超出工具本分）——仓库的 `.gitignore` 里由我们一次性加好 `.graph/` 即可。

**关于"输出格式"这一条，必须拆成两个字段**，因为五个后端能力不一样：

- **`schema`（只有 codex 能用）**：一段格式定义，由 codex 服务端**强制**执行。传给其它四家，桥会直接报错——所以**工具要在发请求之前就拦下来**并给出人话提示。
- **`outputShape`（另外四家用）**：一段写进提问里的格式要求 + 工具做的**弱检查**——只查两件事：**能不能解析成 JSON 对象、必需的几个顶层字段在不在**（用 `Object.hasOwn`，不然要求 `constructor` 这类名字时空对象也会蒙混过关）。**明确不是完整的格式校验，也不查字段类型**（桥本身刻意不带校验器，就是为了避免出现第二套跟 codex 不一致的判定标准；工具也不该去造）。弱检查不过 → 打回重说一次，还不行就报错停下。

### "回执"里记什么

每个环节干完留一张回执，记：**回执格式版本号**、环节编号、**输入指纹**、成没成、结果文件在哪、内容多长、这个会话的上下文用掉多少 token（**cursor 和 kimi 拿不到这个数，要记成"未知"，绝不能记 0**——记 0 会让它们永远显得最新鲜、永远轮不到该换新会话）、花了多久、失败的话错在哪、现场文件落在哪。

**"输入指纹"是这里最关键的一个字段**，得解释一下：把"用哪个 AI + 哪个型号 + 思考多深 + 提问原文 + 角色设定文件的内容 + 在哪个目录"拼起来算一个哈希值。为什么必须有：以后想做"跳过已经干完的环节、只重跑没干完的"，就得先回答"这张旧回执记的，到底是不是**当前这份任务单**的结果"。任务改了提问、换了型号，回执长得一模一样——**没有指纹就会把上一版任务的结果当成这一版的，静默出错，这是最难查的一类错**。

第一版的行为：**同编号回执已存在 → 默认拒绝重跑并报错**（防手滑重复烧钱）。但要留一个"指纹一致就跳过复用、不一致就报错说明任务变了"的开关。**断点续跑本身第一版不做，但这个开关第一天就得在**——它是"回执到底有没有用"的唯一检验，回头再补等于回执白留。

### "保留现场"是一个动作，不是一句口号

桥在**干净退出时会把本次运行的日志目录整个删掉**（源码 `agent-bridge.mjs:5442-5444`），关会话也会删掉那份完整结果文件。所以光说"出错时保留现场"是落空的。硬要求是：

**任何非正常的收场，工具必须在关桥之前，把这三样东西复制到本环节的结果目录里**：① 桥指出的那份日志；② 还能读到的完整结果原文；③ 最后一次状态查询的完整返回（含最近事件）。回执里记下落盘路径。复制一律用**字节直传**、不要"读出来再写一遍"（沿用圆桌记账工具的做法：不改字节、不花 token、不踩 Windows 编码转换的坑）。

### 程序结束时报的"数字"（退出码）

**`node-turn`（命令行，跑一个环节）**——描述**这一个环节**的结局：

- **0** 成功 · **1** 程序自己崩了（没预料到的异常）· **2** 结果格式不合格（打回重说后仍不合格）· **3** 后端 AI 挂了（会话失败或被关）· **4** 超时 · **5** 用法或文件问题 · **6** 遇到没预料到的状态（**停下、保留现场、报告**）

  其中 **3 和 4 有重叠**（后端卡死被超时收掉，既算挂了也算超时），所以要写死判定顺序：**先判超时**（超时是工具自己的动作，看得见），只有桥明确回报"失败/已关闭"才算 3。

**写脚本的时候用不到退出码**——`runNode` 直接返回带 `status` 的回执（`ok` / `contract_error` / `backend_failed` / `timeout` / `unknown`），你自己 `filter` 就行。

**这里有一条不能违反的原则**：**绝不能让"一批里有环节失败"变成一个笼统的整体失败**。因为"一个环节挂了怎么办"是策略、归调用方（项目里圆桌是带缺口继续、loop 是换引擎重开，没有统一答案）。所以逐个环节的结局各自进各自的回执，脚本自己决定怎么处置——这也正是当初砍掉 `fan-run` 的一个附带好处：没有"一批"这个概念，就不存在"用一个退出码表达一批结局"的困境。

最后那条"遇到没预料到的情况就停"是项目一贯的铁律：写死的流程最怕的不是死板，是在没人预料的地方**无限空转**（费钱费时还没人发现）。宁可明明白白停下报错，也不"尽量往下凑"。

### 五个后端各自的脾气不一样

| 后端 | 能力边界 | 派活前必须先确认 |
|---|---|---|
| **Codex** | 只有它的"只读"是**真只读**（系统级沙箱，想写盘也写不进去，三个平台都一样）；也只有它能**强制**输出格式 | — |
| **OMP** | 只读是**软的**（带命令行，理论上能写盘，靠约束不靠强制）；不能强制格式 | 型号要用"提供方/型号名"的全名，别传裸名 |
| **Claude** | 同 OMP：软只读、不能强制格式 | — |
| **Cursor** | 软只读（原生写工具还在）；看不到上下文用量；**内容会上传 Cursor 云端且删不掉**——敏感任务别用 | 型号必须是**带档位后缀**的完整名（比如 `gpt-5.3-codex-high`），裸的家族名未必被接受 |
| **Kimi** | 软只读（原生写工具还在）；看不到上下文用量；会话虽在本地，但**推理仍发往 Moonshot 云端**，敏感内容照样算出境 | 型号用 `kimi-code/…` 别名；**设了"思考多深"也会被忽略**（表面接受、实际不生效） |

由此定几条规矩：

- **第一版任务单只允许"只读"档。但这不等于"不可能改文件"**——只有 codex 是系统级硬拦，另外四家都是软的（cursor 和 kimi 连原生写工具都还在，只靠每轮提示压着）。所以**要硬保证不写盘的环节，任务单里就得点名用 codex**；其余属于"约定不写"，工具管不住。
- **需要"挑刺、当裁判"这种关键判断的环节，别用 cursor 和 kimi**（每轮是短进程，角色设定容易飘），让它们干"分头查"里的普通环节就好。
- **敏感内容的任务，一开始就别把 cursor / kimi 排进去。**
- **脚本开跑前先做一次后端体检**（`bridge.doctor()`），不可用的立刻报错——比开四个会话失败四次便宜得多。但要注明：**体检只查版本号，不查登录状态、也不保证真能起来**，过了照样可能在开会话时挂。

### 谁负责清场、会不会跟主 agent 打架

- **谁关**：工具自己起的桥进程，自己关干净——正常路径是逐个关会话 → 关掉给桥的输入（桥收到结束信号会清理所有会话再退出）→ 等它退出。异常路径见上面"保留现场"和"超时"两条。
- **兜底**：整批收尾后跑一次 `node scripts/agent-bridge.mjs cleanup`，回收抗打断的残留进程。
- **和主 agent 自己的桥互不可见**：工具的会话活在它自己的进程里，主 agent **看不到、也够不着**（主 agent 的"兜底清场"清不到它们）。好处是互不干扰；**坏处是出事了主 agent 帮不上忙——所以工具必须自己收干净，这是硬要求。**
- **别同时榨满机器**：工具在跑 4 个后端的时候，主 agent 别自己再跑重构建或大批委托，两边抢 CPU 会让桥变慢、更容易被误判成卡死。

## 第六部分：什么时候才真正需要这个技能（全文最关键的一节）

### 6.0 先老实承认：那 6 种玩法，光用桥本体就能做

调研里列的 6 种玩法，看着挺唬人，但**每一种今天直接用 agent-bridge 就能摆出来**：

| 玩法 | 今天光用桥怎么做 | 需要本技能吗 |
|---|---|---|
| 分头查、再汇总 | 开 3 个会话 → 各发一条 → `wait(mode:"all")` → 再开一个汇总 | **不需要** |
| 一个干、一个挑刺 | 开一个生产者 → 换个引擎再开一个评审 | **不需要** |
| 多个抢答、选最好 | 开 N 个会话发同一道题 → 再开一个评委 | **不需要** |
| 先分类、再分流 | 开一个会话做分类 → 看结果自己决定下一步 | **不需要** |
| 多生成、再筛选 | 开几个会话各出候选 → 自己合并去重 | **不需要** |
| 反复干到好为止 | 对着同一个会话反复发消息 | **不需要**（而且 loop 技能更合适） |

**所以这 6 种玩法证明不了这个技能有存在价值。** 根子在于：**这 6 种说的是"任务长什么形状"，而 graph 工程说的是"流程由谁承载"。** 形状用桥就能摆出来——**换载体才是 graph 工程的本事。**

### 6.1 graph 工程真正特殊在哪：换的是"流程的载体"

调研文章第 37 行说得很直白：这项设计的主要价值**不是简单增加 Agent 数量**，而是把原本占用主 agent 上下文的**调度逻辑转移到代码中**——工作计划存在脚本里、中间结果存在 JS 变量里、主会话通常只收最终结果。

**一句话：把"流程"从"活在主 agent 的脑子里"，换成"活在一段 JS 和它的变量里"。**

两种载体的差别（这张表才是本技能存在的理由）：

| | 主 agent 手工驱动（今天用桥的做法） | 写一段 JS 编排 |
|---|---|---|
| **流程写在哪** | 主 agent 的上下文里——会被后面的内容挤掉、会漂 | 一个文件里——不会忘、不会漂 |
| **中间结果去哪** | **每一份都进主 agent 的上下文**（3 家各吐 5000 字，就是 15000 字全进） | JS 变量 + 磁盘文件，**主 agent 一个字都不用看** |
| **20 个环节** | 上下文被中间结果塞满，开始漏东西、判断力下降 | 无所谓，20 个和 2 个一样 |
| **循环、条件** | 靠模型自觉——**而且可能被 prompt 说服跳过** | `for` / `if`——**不会被说服** |
| **能不能重跑** | 不能，那是一次性的对话 | 能，脚本还在，换个目录再跑一遍 |

倒数第二行不是理论：**项目自己的演化文档里已经实证过**——文字驱动的控制流**会被说服偏离**（当时花了整整一轮去堵"模型被全局偏好文件带偏、把严格交替和无人值守当场绕过"的口子），而 `for` 循环不需要这种防护，它不会被说服。

### 6.2 判据：什么时候该从"手工驱动"切到"写脚本"

**一句话判据：问自己——"这个流程，主 agent 能不能一边记着全部中间结果、一边不出错地走完？"**

- 能 → **别用本技能**，直接用桥，省事。
- 不能 → 才轮到本技能。

具体的切换线（命中任意一条就该写脚本）：

| 信号 | 为什么 |
|---|---|
| **环节数 ≥ 5~6** | 3~4 个手工还行；再多，光记"谁跑完了谁没跑完"就开始出错 |
| **需要循环**（不确定要几轮） | 手工循环没人数轮数，容易多跑一轮或少跑一轮 |
| **需要按结果分支** | "如果 A 说有问题就派 B，否则跳过"——这种判断写成 `if` 才可靠 |
| **中间产出很大**（每个环节几千字） | 手工驱动会把这些正文全灌进主 agent 上下文，这正是要避免的 |
| **这个流程要跑不止一次** | 脚本能重跑，对话不能 |

反过来说：**环节少、一条直线走完、产出又不大——这种就老老实实用桥，别为了用工具而用工具。**

### 6.3 一个真正需要脚本的例子

上面那 6 种玩法的例子都是 2~3 个环节的玩具，手工就能干。下面这个才是手工干不了的：

**任务**：审计 20 个文件；每发现一个问题，要 3 个不同引擎交叉验证，只保留 2 票以上的；最多 3 轮，直到某轮没有新发现为止。

```js
import { withBridge } from ".../node-core.mjs";

await withBridge(async (bridge) => {
  const seen = new Set();
  const confirmed = [];

  for (let round = 1; round <= 3; round++) {          // 循环：写死上限 3 轮
    const found = (await Promise.all(                 // 扇出：20 个文件同时查
      FILES.map((f) => bridge.runNode({ agent: "codex", prompt: `审计 ${f}`, /* … */ }))
    )).flatMap(readIssues);

    const fresh = found.filter((i) => !seen.has(key(i)));   // 去重：普通代码，不叫 AI
    if (fresh.length === 0) break;                          // 收敛条件：没新发现就停
    fresh.forEach((i) => seen.add(key(i)));

    for (const issue of fresh) {                      // 交叉验证：每个问题 3 个引擎投票
      const votes = await Promise.all(
        ["kimi", "omp", "claude"].map((a) =>
          bridge.runNode({ agent: a, prompt: `这个问题成立吗：${issue.desc}`, /* … */ })));
      if (countYes(votes) >= 2) confirmed.push(issue); // 计票：普通代码
    }
  }

  return { confirmed, rounds: round };                // 主 agent 只收到这一个结果
});
```

**这段脚本体现了 graph 工程的全部特点，而且每一条手工都做不到**：

- **环节数量**：最坏情况 20 × 3 轮 + 每个问题 3 票，上百次委托——手工驱动早就把主 agent 上下文撑爆了。
- **中间结果不进上下文**：20 份审计报告、上百张投票，全在 JS 变量和磁盘里，主 agent 只看见最后那个 `confirmed`。
- **循环有硬上限、有收敛条件**：`round <= 3` 和 `fresh.length === 0`，不靠谁自觉。
- **不需要判断的活全用代码**：去重（`Set`）、计票（`countYes`）、过滤——一次 AI 都没叫。
- **可重复**：换一批文件再跑一遍，脚本原样不动。

**这才是"适不适合做 graph 工程"这个问题真正的答案**——不是能不能摆出那 6 种形状，而是**能不能把这种规模的流程从主 agent 脑子里搬出去**。

### 6.4 几条写脚本时的纪律

1. **循环一定要写死最大轮数 + 一个收敛条件**（像上面的 `round <= 3` 和"没新发现就停"）。不然没人叫停就一直烧钱。
2. **不需要判断的活用代码，别叫 AI**：合并、去重、排序、计票、按条件路由。这是调研里明确的原则，也是省钱省时的大头。
3. **结果靠文件路径传，别把正文贴进下一个提问**（大家在同一个工作目录，让它自己读）。贴正文既费钱又容易被截断。
4. **汇总、评审、挑刺的环节一定换引擎**——自己评自己没意义，这是项目一贯的规矩。
5. **一次并行别超过 4 个**（默认值）：不是机器扛不住，是怕挤垮主 agent 自己那条桥连接。
6. **遇到没预料到的情况就停下报告**，别写"看不懂就再跑一遍"的重试。
7. **敏感内容的任务别排 cursor / kimi**（内容出境，cursor 那边还删不掉）。
8. **别在脚本里造引擎**：不要写 plan 格式解析、不要写通用的节点依赖图。真需要那些了，说明该把这段脚本沉淀成正式工具（见第十部分）。

## 第七部分：这一版明确不做的事

- 不做**通用流程引擎**：不发明 plan / DAG 格式、不写依赖解析、不写调度器。
  ⚠️ **别把这条读成"不支持循环和分支"**——你在自己那段 JS 里爱怎么 `for`、怎么 `if` 都行（见第六部分）。不做的是"**替你把循环分支抽象成一套通用格式**"那件事。
- 不做"改文件"的环节，不做多人改文件防冲突那套。
- 不做"自动往下走"（等齐之后干什么，交给临场判断）。
- 不做**跨调用**共用常驻后台进程（一次 `withBridge` 内部用一个进程管几个会话不算——那是"自己起、自己关，全程只有它一个主人"，见第五部分）。
- 不做跨程序的断点续跑（但回执和输入指纹照留，为以后铺路）。
- 不做可视化页面、不做运行中途找人确认。
- **不动现有的三个技能**（dev、roundtable、loop）——它们照常用。这个新技能是并排的第四个、更底层的零件。概念上确实有对应（dev 的双评 ≈ "一个干一个挑刺"、roundtable 的分头发言 ≈ "分头查再汇总"），但**只是概念上像，现在绝不动手改它们**：那三个技能已经在用、跑得通，各自的规矩还在调整，硬改成"来调用新技能"只会添乱。这个新技能真正省下的，是**下一个新场景又得从头手抄一遍环节执行代码**的成本。

为什么定这么死的边界？讨论里两个 AI 都警告过同一个坑：**一旦开始"顺手加个重试、顺手加个缓存、顺手加个流程图"，最后会造出一个比 Claude 自带的还弱的引擎，白费劲。**

**还有一条要认清**：这两个新工具虽然形态上像圆桌那两个记账小工具（都是"把机械动作抽成命令行工具"），但**风险不是一个量级**——圆桌那两个只动文件、不碰桥、不起进程，出错最多是记账写歪；这两个新工具要自己拉起一棵进程树并负责关干净，**出错会留下烧钱的残留进程**。所以它们必须比圆桌那两个多做三件事：**超时后主动打断、退出前把现场落盘、收尾跑一次残留检查**。

---

## 第八部分：怎么验证它真的有用（不然就别往下做）

**第 0 关（推送前的闸门，不烧一分钱）**：用仓库里现成的五个假后端跑完整链路——正常、超时、后端挂、格式不合格、没预料到的状态，五种走法各一遍。这一关跟仓库既有做法一致，承担回归职责；下面几条真跑只作最后的真实性确认。

**真跑验证**：

1. **真实多 AI 协作**：让 codex、omp、claude 三家各自只读地审计本仓库同一个问题。验证：回执齐全、存下来的结果和实际内容一字不差、跑完之后没有残留后台进程和僵尸会话、主 agent 只收到那张汇总清单。
2. **故意让一个环节失败**：半路杀掉其中一个后端进程。验证：其余的照常等齐、都被正常收尾、汇总清单里那一条标明失败、而且**没有自动去启动下一步**。
3. **故意让输出格式错**：让一个 AI 在规定格式下偏偏吐大白话。验证：打回重说一次还不行就报格式错、毛病记进回执、绝不糊弄过关。
4. **超时收场**：让一个环节故意跑过头。验证：工具确实先打断再关会话，退出后机器上**没有该后端的残留进程**（用 `cleanup` 复查，应该无事可收）。
5. **重复跑防呆**：同一个编号、同一个目录再跑一遍（没说要覆盖），验证它会拒绝，而不是傻乎乎又干一遍。

**最硬的一条验收**：拿这套工具**重写一个现有的真实场景**（比如 dev 的并行双评），跟现在"手册手动操作"的做法比三个数：① 主 agent 的上下文多用了多少 token；② "漏设超时 / 用了会卡死的等法"这两类错的发生次数（历史上正是这两条被抄了三遍）；③ 总耗时。**第 ① 项没有明显下降就停，不为了做而做。**

## 第九部分：名字和触发边界

技能名定为 **`agent-bridge-graph`**（已拍板）。名字对上你和社区已经在用的"graph"说法，也认领了长远方向。

**代价是必须自己消歧**：既然第一版根本没有"图"（见第三部分小结），名字就会让人产生过高期待。所以**说明书开头第一句必须写清楚**：

> 这一版提供的是「多 AI 协作的积木块」——把"叫一个 AI 干一件事"和"几个 AI 分头干、等齐汇总"做成可靠的命令行工具。**这一版不提供流程图引擎，串环节仍由你自己完成**；也不是 Claude Code 自带的那个「动态工作流」。

**触发边界**（说明书开头那段用来判断"什么时候该唤起这个技能"的话）草案：

> 用 agent-bridge 把「一个环节 = 一个 AI 干一件事」做成可靠的命令行工具，并支持「几个不同引擎的 AI 同时各干一件事、等齐后汇总成清单」。仅当用户明确要求「多个不同 AI 分头干再汇总 / 一个 AI 挑另一个的刺 / 几个 AI 抢答同一题」时使用。普通的并行委托直接用 agent-bridge 本体；要多轮讨论收敛用 roundtable；要合同驱动的自动交付循环用 loop。**不要因为出现「工作流 / workflow / 图 / graph」这类词就触发**——Claude Code 自带的 Workflow 是另一回事。

最后一句尤其重要：这个技能的名字跟 Claude Code 原生功能的叫法高度重合，不写死反例，几乎一定会被误唤起。

---

## 第十部分：以后会怎么长大（现在不做，只记方向）

一步有一步的触发条件，绝不提前：

1. **现在**：先做这两个小工具。因为"每次手抄环节执行代码"这个痛点已经实实在在出现三遍了。
2. **以后**：等项目里那个"无人值守自动循环"的规矩**连续跑通好几次都不用再改**了，再把那个循环的内环写成真正的调度代码。到那时该怎么写，是从"真跑过很多次"里总结出来的，不是拍脑袋设计的。
3. **更以后**：如果真的又冒出第二个"需要写调度代码"的场景，再从前面那段代码里提炼通用的部分。**如果一直没冒出第二个场景，那就说明本来也不需要通用引擎**——不做反而是对的。

背后是一条原则：**别凭空设计抽象的东西。** 换句话说：图的基本形状确实是稳定的，写死它不算"把会变的规矩写死"。问题在别处——**没跑过就先造通用件，等于凭空猜一个抽象。**
