# session viz「装锁」设计 —— 2026-08-04

**范围**：只回答「锁具体怎么做」这一件事，是 `BACKLOG-2026-08-03.md` 一、开工顺序第 1 步的细化。
第 2、3 步（发送本身、`source` 第三档、规范文档）不在这份里。

**结论先说**：可行性评估里「走底层现成的发送通道，一行新逻辑都不要另写」这句话**要修正**。
看了代码之后发现，那条通道够不着页面——中间缺一段，锁得先接完这段线才有地方挂。

---

## 一、被推翻的假设：serve.mjs 摸不到 sendMessage

`sendMessage()`（真正能给 agent 发消息的函数）活在桥进程 `agent-bridge.mjs` 里，操作的是这个进程
内存里的会话对象（子进程的 stdin 之类）。

`skills/agent-bridge/viz/serve.mjs` 是完全独立的另一个进程——用户在终端手动敲命令起的
（`node serve.mjs <目录>`），从头到尾只做一件事：轮询 `VIZ_DIR` 下桥写的 `state.*.json`，
转发给浏览器。它从没连过桥，也没有任何办法调用桥进程内存里的东西。

所以浏览器发一条消息，要经过两跳：**浏览器 → serve.mjs → （缺的一段）→ 桥进程 → 真正发给 agent**。
第二跳今天完全不存在。这不是「往哪装锁」的问题，是先要把线接上，再谈锁在哪个环节合适。

## 二、接线：两个方案

### 方案 A：新开一条进程间通道

桥进程监听一个本地 socket（Windows 是 named pipe），serve.mjs 当客户端连上去转发请求。

- 实时，没有轮询延迟
- 但多一种协议、多一个同样需要上锁的监听端口/管道——鉴权工作量翻倍：两条通道都要单独挡住
  「本机任意进程/网页能发指令」这件事
- Windows 和 macOS/Linux 的本地 IPC 原语不同，多一层平台分支

### 方案 B（推荐）：复用 `VIZ_DIR`，加一对信箱目录

`VIZ_DIR` 本来就是桥专属的临时目录（`mkdtemp` 出来的，所有权已经是起桥的这个系统用户），
桥进程本来就有轮询节奏（`pruneTimer`、`watchdog` 那两个 `setInterval`，见
`scripts/agent-bridge.mjs:6832/6859`）。加两个新的命名空间：

```
VIZ_DIR/
  inbox/<sessionId>/req-<id>.json     ← serve.mjs 写，桥读并删
  outbox/<sessionId>/resp-<id>.json   ← 桥写，serve.mjs 读并删
```

流程：serve.mjs 收到一条合法的追问请求 → 写进 `inbox/` → 桥进程的轮询发现新文件 → 做权威检查
（会话是不是真的闲着、有没有没取走的结果）→ 通过就调内部那份 `sendMessage()` 逻辑，
不通过就直接写拒绝理由 → 结果写进 `outbox/` → serve.mjs 下一拍轮询到，通过现有的 SSE 通道
推给页面（新增一种事件帧，跟 `state`/`progress`/`control` 并列，不复用它们）。

**为什么选这个**：

- 不开新端口、不引入新协议，新增攻击面只有「多两个子目录」，而不是「多一个监听服务」
- 复用 `VIZ_DIR` 现有的操作系统级权限——今天「同机其它进程能读到」这句话已经承认了读的风险，
  但**写**这个目录还有目录所有权挡着，不是同机任意进程都能写
- 跟现有轮询+SSE 的架构风格一致（`serve.mjs` 本来就是「隔一会儿看一眼文件变了没有」这套逻辑）
- 代价是几百毫秒的轮询延迟——但这本来就是「对着已经闲下来的会话追问」，不是要打字实时对话，
  这点延迟感觉不出来

**要在文档里说清楚的一句话**：`docs/STATE-session-viz.md` 里「viewer 是搬运工，不是第二个
writer」这条纪律，指的是 `state` 这个帧——`inbox`/`outbox` 是新的命名空间，写的是「请求」和
「回执」，不是 `state`，不违反那条纪律的本意，但字面上容易被读成矛盾，得单独写一句澄清，
不然以后有人以为这条纪律被绕过去了。

## 三、HTTP 那一层的锁——原来说的「装锁」

不管走哪种接线，浏览器到 `serve.mjs` 这一跳都要挡。真正要防的不是「同机其它进程」
（那个风险在只读时代就已经被接受了），而是**另一个网页**：你浏览器随便开的一个标签页，
只要知道端口号，就能悄悄发一个跨站请求过来，让你的 agent 收到一句它认不出来源的话。
可行性评估里说的三样缺一不可，具体做法：

**1. 凭证——不放 URL，塞进页面本身**

`serve.mjs` 启动时生成一个随机值（`crypto.randomBytes(32)`），跟今天打印访问地址一样打在
stdout，但**不拼进 URL**。原因：URL 里的东西会进浏览器历史、会在页面有出站链接时通过
Referer 头泄漏。改成响应 `GET /` 时把它注入到 HTML 里（`<script>window.__VIZ_TOKEN__="…"` ），
页面自己的 JS 读出来存在内存里，之后每次发送请求放进自定义请求头（比如 `X-Viz-Token`）。

这样做不会让「谁能拿到凭证」的范围变大——今天只读路由本来就是「谁能连上这个端口，谁就能看到
这次运行的全部委托内容」，凭证塞进同一个响应里，暴露面跟现状完全一样，只是**现在多了一个后果**
（能拿到凭证的人现在还能发消息），这个后果靠下面两条再收一道。

**2. 校验来源**

每个 POST 请求必须带 `Origin: http://127.0.0.1:<端口>`，跟自己一致才放行；缺失或不一致一律拒。
自定义请求头（`X-Viz-Token`）会让浏览器把这类请求当成「非简单请求」，发之前先发一次 `OPTIONS`
预检——只要服务端不回放行别的来源的 CORS 头，浏览器自己就会在预检这步拦下来，请求根本发不出去，
不需要等到服务端逻辑去挡。服务端仍然要做 Origin 校验，防的是不遵守 CORS 的非浏览器客户端。

**3. 限制请求类型**

新增的发送路由只接受 `POST` + `Content-Type: application/json`，请求体大小硬顶（`/file` 那条
路由已经有类似的字节上限模式，抄一份）。其余路由（`/events`、`/file`、`/`）维持只认
`GET`/`HEAD`，这条今天已经满足，不用改。

**三条为什么缺一不可**：只有凭证挡不住「凭证泄漏后的伪造来源」（凭证一旦被读到，攻击者可以
自己拼一个跨站请求带上它，如果不查 Origin 就会放行）；只有来源校验挡不住「凭证被读到、
Origin 也伪造成功」的非浏览器攻击路径（比如同机某个脚本，不受浏览器 CORS 约束）；两条都有
才是「即使某一条失效，另一条兜住」，不是三条里随便留一条。

## 四、这道设计对下一步（第 2 步：页面能发消息）先占的两个位置

- **「有没取走的结果」这道闸的权威判断必须在桥进程做**，不能只信页面自己看到的快照——页面
  看到的 `state.*.json` 有轮询延迟，存在竞态窗口。快照里 turn 的 `collected` 字段
  （`scripts/viz-writer.mjs` 里能看到这个字段已经在记）可以直接拿来做**界面上的置灰判断**
  （用户体验意义上的提前拦），但拦截生效点必须在桥处理 `inbox/` 请求那一步重新查一遍，
  不能只信页面传过来的「我看到是闲的」。
- **这功能天然只在观测台开着的时候存在。** 没开 `AGENT_BRIDGE_VIZ` 就没有 `VIZ_DIR`，
  没有 `VIZ_DIR` 就没有 `serve.mjs`，整条链路无从谈起——不用额外做「功能开关」，
  它跟观测台共用同一个开关是自然结果，不是刻意设计。

## 五、已拍板（2026-08-04，用户）

1. **接线走方案 B**：复用 `VIZ_DIR`，加 `inbox/`/`outbox` 这对信箱目录，不新开监听端口。
2. **凭证走 HTML 注入，不进 URL。** `serve.mjs` 响应 `GET /` 时要做一次字符串替换
   （现在 `sendLocal()` 是纯读文件转发，要改成读文件 + 替换占位符）。

   **凭证说清楚是什么，免得字面意思带偏**：不是要用户记的密码，是 `serve.mjs` 启动时随机生成
   的一串长字符（`crypto.randomBytes(32)`），只活在这个进程的内存里，进程一关就作废，不写文件、
   不写死在代码里。页面加载时它被注入进 HTML，页面自己的 JS 存进内存，之后每次发送请求带上它；
   `X-Viz-Token` 校验就是拿这个值比对。**「一次性」指的是「每次起一次服务就重新生成一次，
   不是所有观测台永远共用同一个固定值」，不是「用一次就失效」的验证码语义**——上一版措辞
   沿用了可行性评估的原话，容易读岔，这里改清楚。
3. **`inbox`/`outbox` 轮询间隔跟现有 `POLL_MS`（400ms）同量级**，不引入 `fs.watch`。
