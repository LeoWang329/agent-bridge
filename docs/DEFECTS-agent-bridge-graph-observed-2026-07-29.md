## D1 · `viz` 开关在文档里根本不存在（**当场挡住了用户**）

**事实**：`withBridge(fn, { viz: true, outDir })` 会建归档 scope、**自动 fork 一个 viewer**、
把 URL 挂在 `bridge.vizUrl` 上，起不来还会 fail-fast。功能完整且已上线。

**缺陷**：这个选项在两份对外文档里**都不存在**。

| 文档 | 写了什么 |
|---|---|
| `SKILL.md` | `opts`：`{ bridgePath?, env?, initTimeoutMs?, onStderr?, maxConcurrent?, maxConversations? }` —— **没有 `viz`** |
| `tools/README.md` §「`withBridge` / `startBridge` 的选项」 | 只有 `maxConcurrent` / `env` / `bridgePath` —— **没有 `viz`** |
| `SKILL.md` 唯一一处 viz 提及 | 一行 shell，`VIZ_OUT_DIR=…/viz/sample` —— 指向**样例目录**，读者会以为"只能看样例" |

**当时挡住了什么**：用户在两轮 graph 跑到一半时说「现在有 graph 在跑吗，启动一个可视化给我看看」。
我照文档找不到开归档的办法，只能回答「那个 run 起的时候没开归档，retrofit 不了」。
**功能明明在，而且默认就会把 URL 打给我。**

**为什么这条排第一**：其余几条是摩擦，这条是**能力对使用者不可见**。
一个已经上线、过了复审、有专属 `docs/EVENTS-graph.md` 合同的观测台，因为选项表漏了一个键而等于不存在。

**已修**：`tools/README.md` 的选项表补了 `viz` / `vizPort` / `outDir` / `maxConversations`。
两份文档都加了当初没想到的那一句 —— **它是起桥时的开关，跑到一半 retrofit 不了**。
这才是当时真正挡住人的东西：不是「找不到键名」，是「以为能事后补」。
`VIZ_OUT_DIR=…` 那条命令也改了口径（它是**单独打开一份已有归档**），并给了指向自己 `outDir` 的写法。

## D2 · 回执没有可机读的失败分类，"欠费"和"瞬时错"分不开

**事实**：回执的 `status` 只有五档 `ok | contract_error | backend_failed | timeout | unknown`。
额度耗尽、限流、后端崩溃、登录过期**全都落进 `backend_failed`**。

**缺陷**：调用方要区分「**要人去充值，重试毫无意义**」与「429 / overloaded，该退避重试」，
只能自己去 `scene` 里的 `session.log` / `answer.txt` 做**字符串匹配**。

**当时的实际代价**：本次三个编排脚本里，每一个都复制粘贴了同一段：

```js
const HALT_MARKERS = ["欠费","余额不足","insufficient_quota","payment required","402", …];
const RETRY_MARKERS = ["429","rate limit","overloaded","econnreset", …];
function triage(receipt) { /* 读 scene 的每个文件、拼起来、toLowerCase、includes */ }
```

这段东西：**每个使用者都要重造一遍**、**跨后端跨语言脆得离谱**（换个模型换句措辞就漏）、
而且**判错的方向很贵**——把欠费判成瞬时错，就是在余额为零时把钱包按着继续刷。

**这不是"策略归调用方"能解释掉的。** skill 明说「一个环节挂了怎么办是策略、归你」，
这话对**处置**成立（继续 / 换引擎 / 停），但**分类**不是策略，是**事实**——
而事实只有桥和后端看得见，调用方是最没资格猜的那个。

**已修**：回执加 `failureKind`（封闭 7 档，比建议多一档 `internal` —— 派发/收尾自己炸了不是后端的错，
混进 `backend_crash` 会诱导去重试一个本地 bug）+ `failureEvidence`。

**一处与建议不同，要说清**：判据没能放进「各后端 adapter」—— 桥与五个后端**都没有机读的失败码**，
真相只存在于后端吐出来的那句话里。所以它仍然是**按错文做的启发式**，放在 `classifyFailure()` 一处。
换来的三件事：只做一次、可审计（`failureEvidence` 说清凭哪段判的，而不是给一个不容置疑的标签）、可回归。
**没有过度承诺**：文档明写它不是协议级保证。判据顺序也写死了 —— 先判「重试没用」的（quota/auth）
再判「该重试」的（rate_limited），因为判错方向很贵：把欠费当瞬时错，就是在余额为零时继续刷。

## D3 · 失败节点无法原地重试，换 id 就破坏产物路径契约

**事实**：`reuseIfSame` 只复用 `status === "ok"` 的回执；失败回执不可复用。
同 id 重跑要么 `force`（**覆盖并丢弃现场**），要么换一个 id。

**缺陷**：换 id 之后产物落在 `nodes/<id>-r1.md`，而下游代码引用的是 `nodes/<id>.md`。
skill 自己的纪律第 3 条要求「结果靠文件路径传」——**重试恰好把那个路径改掉了**。

**当时怎么绕的**：我写成 `id: \`${spec.id}-r1\``，然后**只用返回的回执对象**、
不再按约定路径去取——等于放弃了纪律第 3 条那条通路。
如果这张图更大、下游节点是靠路径读上游产物的，这次重试就会静默读到一个不存在的文件。

**已修**：`retryFailed:true` 就是这条路，但按前缀搬**整套**产物而不是只搬 `.md`/`.receipt.json` ——
`.scene/`、`.a<n>.md`、`.diff`、对话的 `.t-*` 一律跟着走。规则是「`<id>.` 开头的都搬」，
只排除两样：此刻攥着的 `<id>.lock`，以及**已经归档过的** `<id>.f<m>.*`（否则第二次重试会把第一次的审计原件套进去）。
**刻意不维护一张后缀清单** —— 那种清单下次新增一种产物就会漏掉它。

两处建议里没有的决定：
- 上次是 `ok` 时 `retryFailed` **当没这个开关**（交给 `reuseIfSame`）。于是两个开关同传正好是断点续跑
  要的语义：**好的复用、坏的重试**，而好的绝不会被悄悄重跑掉。
- **`access` 为 write 的环节直接拒绝**。失败的 write 环节会把 worktree 与分支**原样保留**
  （里面可能有还没人看过的改动），原地重试就得先动它们 —— 那个决定必须由人做。
  静默删掉别人保留的分支，是这个仓库明确记过的危险动作。

## D4 · `Promise.all` 是自然写法，但会把并行节点的部分成果丢掉

**事实**：`runNode` 不为环节失败抛异常。但 skill 同时要求调用方自己决定处置策略，
而**任何会抛的处置**（例如 D2 那段分诊，或纪律第 6 条要求的「停下报告」）
一旦包在 `Promise.all` 里，第一个抛出就让整个 `all` reject。

**后果**：其余节点**仍在后台跑**，直到 `withBridge` 收尾才被回收；
它们的产出**有没有写完、写到哪了，调用方一无所知**。
skill 的纪律第 6 条说「遇到没预料到的情况就停下报告」，但**没有原语能报告"已经完成了哪些"**。

**当时的实际形态**：我的两个扇出脚本都是 `await Promise.all(jobs)`，
而 `runGuarded` 会抛 `Halt`。这次运气好（没触发），但形状本身是错的——
正确写法是 `allSettled` + 自己收敛，而**文档里没有任何一处提示这一点**，
示例 `examples/hetero-audit.mjs` 用的也是 `Promise.all`。

**已修**：两条都做了 —— 加了 `bridge.runAll(specs)` 原语，**并且**把 `examples/hetero-audit.mjs`、
`templates/wave.mjs`、SKILL.md 的主力示例全改用它。只改文档不改示例，等于说一套教另一套。

建议里没写的那半：**用法错必须在派发任何环节之前抛**。所有 spec 先过一遍 `normalizeSpec`，
那时一个环节都还没跑，抛出去不丢任何东西；而一个拼错的字段也不该伪装成「某个环节失败了」混过去。
派发之后再抛的（撞锁、内部异常）才归一成 `unknown` + `dispatchError` + `failureKind` 为 internal，
**并且不中断别人**。`status` 仍然只有那五档，不新增第六档。

## D5 · `reask` 的代价与节点时长成正比，但它是默认开的

**事实**：`reask` 默认 `1`，格式不合格打回重说一次。

**缺陷**：文档把 `reask` 描述成「全系统唯一的 retry」，但没说它对时间预算意味着什么。

**当时的实际代价**：`samples` 节点（claude，`outputShape` 弱检查）第一次输出 197 字节不合格，
`a1` 被打回，`a2` 才过 —— 这一轮总耗时 1092 秒里，**相当一部分是这次重说**。

**⚠️ 原始报告里「一次 reask 就是再花 15 分钟」这句话是错的**，我第一次修的时候照抄了它，
还在复审第 1 轮里据此驳回了 codex 的反对意见 —— **驳错了**。第 2 轮它给了行号，我核了代码：
`startClock` 在整个 `runTurn` 里**只调一次**（`node-core.mjs:2606`），而 reask 是同一个
`while` 循环（`:2704`）里的下一次尝试，还要先过 `remaining() > 0`。
两次尝试**共用同一份 `timeoutMs`**，墙上时间不会翻倍。

我读错的地方：代码注释里说「每一轮各自起钟」，那个「轮」指**对话的轮**（`conversation` 里
每调一次 `turn()`），不是一轮内部的 reask 尝试。

**已修**：SKILL.md 那一节按真实语义重写了 —— 真正的代价不是「时长 ×2」，而是
**同一份预算要装下两次尝试**：第一次跑掉 12 分钟、预算 15 分钟的话，第二次只剩 3 分钟，
于是它更可能**超时**，而不是「再来一次完整的机会」。按「最坏 2×」排期会高估耗时，
按「一次尝试的时间」设 `timeoutMs` 又会让 reask 注定跑不完。替代路径照旧：
**显式 `reask: 0`，把重试放到编排层**。没有改默认值：改了会让「格式偶尔抖一下」这种常见情况变吵。

## D6 · 「要强格式」× 「要非 codex 引擎」这个组合的后果没写清

**事实**（已文档化）：`schema` 仅 codex；其余四家只能用 `outputShape` 弱检查
（能不能 parse + 顶层必需键在不在）。

**缺陷**：两条分开都写了，**组合起来的后果没写**——
「我要机读输出，但这个活儿该给 claude 干」时，你实际拿到的是
**弱检查 + 赌一次 reask**，而不是任何形式的保证。

skill 现在的措辞（「弱检查不是完整校验，别指望它给出 codex 那种保证」）说的是**强度**，
没说**该怎么办**。实践里的答案是：要么改派 codex，要么接受可能白跑一轮。

**已修**：补的不是一句，是一张**处置**表（机读更重要 ⇒ 改派 codex；这活儿非它不可 ⇒ 接受弱检查 +
可能白跑一轮，并把解析失败当**正常分支**写进编排）。末尾点明：「弱检查不是完整校验」说的是**强度**，
这张表说的是**该怎么办** —— 拿不准就选第一行。

## D7 · 一个 `runNode` 的 `prompt` 是**唯一**的信息入口，长范围界定只能靠字符串堆

**事实**：给复审者划范围（"只审这五份"、"这几类明确不在范围内"、"别重新讨论已定的取舍"）
在实践中占了 prompt 的一多半，而且**每一轮都要重写一遍**。第 2 轮我把公共部分抽成
`COMMON` 常量、再拼两个视角——这是普通 JS，工具没拦着，但也没给任何支撑。

**当时挡住了什么**：第 1 轮的 13 条发现里有 3 条越了界（评的是已定取舍或既有代码），
是我在 prompt 里写了"越界的一律不要写"之后才收住的。范围界定写漏一句，
就得为无效发现付一整轮的钱和时间。

**为什么值得修**：范围界定是**复审这个用法**的固有部分，不是某个人的偏好。
但它现在和任务本身混在同一个字符串里，既不能复用，也没有任何东西提醒你"这块你没写"。

**已修**：就是这个形状，`scope: {include, exclude, outOfBounds}`。**不做范围校验器**（这条建议照采纳）。

实现上一个关键决定：范围段拼进**冻结的正文本身**，而不是另立一个指纹字段。这样三件事一次都成立 ——
①进 `specHash`（改范围 = 换任务单，旧回执不该被复用）；②归档里那份输入原件**就是真派发出去的字节**
（否则事件在描述一份从未被派发过的输入）；③`inferDeps` 扫得到里面的路径（`include` 里的文件本来就是依赖）。
另外：`scope` 的键是**封闭清单**，`includes`（多个 s）这种笔误当场拒绝 —— 静默忽略它，
你会以为范围界定生效了，然后为无效发现付一整轮的钱和时间（这正是 D7 当时的实际代价）。

## D8 · 并行节点的**部分成功**没有第一等的表达（D4 的另一面，但更常见）

**事实**：第 2 轮我用两个视角并行审同一批代码。写法是 `Promise.all([mk(a), mk(b)])`。
`runNode` 不为节点失败抛异常，所以 `Promise.all` 这里是安全的——**但这是巧合，不是设计**。
只要有一个环节我用了会抛的写法（比如自己 `throw` 在 map 里），另一个已经跑完几十分钟的
复审结果就一起没了。

**当时挡住了什么**：没挡住，但我为此专门检查了一遍 `runNode` 的异常契约才敢这么写——
而这正是"要靠读源码才敢用"的信号。

**已修**：没有放在 `examples/` 里当小工具，而是做成了**桥的原语** `bridge.runAll`（见 D4）——
放在示例里的东西，抄的人会改、不抄的人看不见；放在原语里它就是唯一推荐写法。
SKILL.md 的组合纪律新增第 2 条，措辞就是建议里那句：**并行收口一律用 `runAll`，别直接 `Promise.all`。**

## 附：这一天里**没有**出问题的部分（同样值得记）

- `reuseIfSame` 的指纹复用**按预期工作**：改 prompt 会拒、不改会复用。
- `withBridge` 的收尾确实等满了强杀窗口，三轮跑完**零残留进程**。
- `maxConcurrent` 的排队是透明的，不需要自己搓限流。
- 三路并行侦察各读 6000 行 core，**anchorStatement 全部经报告方核过"函数内恰好一次"**，
  我抽查了若干条，没有一条编造。
- 用**隔离 cwd + 时序**（让被审对象此刻还不存在）来强制独立性，这个用法 skill 没写，
  但工具本身完全支撑得住——`cwd` 是每节点独立的。**这条不是缺陷，是可以写进 SKILL.md 的用法。**
