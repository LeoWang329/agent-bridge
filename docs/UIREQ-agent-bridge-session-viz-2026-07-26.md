# Agent Bridge 委托会话史 —— UI 需求文档（给设计师）

**日期** 2026-07-26 · **修订** v4（三轮技术复审后定范围）
**交付物** 一套可交互 UI 原型
**技术方案** 见 `docs/DESIGN-agent-bridge-session-viz-2026-07-26.md`（设计师不必读）

---

## 0. 一句话

一个**只读的本地观测台**：一位「主 AI」在工作时会把子任务派给若干个「子 AI」去跑，这个页面让人看到——**派了哪些、谁还在跑、每一轮问了什么、答了什么**。

---

## 1. 先建立几个概念

这五个词会贯穿全文，原型里也应该用这套词（不要另起名字）：

| 词 | 是什么 | 类比 |
|---|---|---|
| **主 agent** | 用户直接对话的那个 AI，它是派活的人 | 项目经理 |
| **会话（session）** | 主 agent 拉起的一个子 AI 实例，有自己的身份和记忆 | 一位被指派的同事 |
| **引擎** | 这个子 AI 是哪家的：Codex / Claude Code / Oh My Pi / Cursor Agent / Kimi Code | 同事来自哪个团队 |
| **轮次（turn）** | 一次「发问 → 作答」。同一会话可以问很多轮，它记得前面聊过什么 | 一次对话往返 |
| **运行（run）** | 主 agent 的一次上线周期。它关掉，这一批会话就都结束了 | 一个工作日 |

**层级：** 一次 run → 多个会话 → 每个会话多个轮次 → 每轮有 **输入 / 输出** 两段。

### 一条会影响文案与空态的前提：记录是临时的

这些内容**只在主 agent 在线期间存在**。它一关，记录连同临时文件夹一起删掉，那次 run 就永久消失了。

这是有意的设计（不在用户电脑上长期留存对话内容），不是缺陷。对 UI 的三点影响：

1. **页面只服务"当前这一个 run"**——没有历史列表、没有归档、没有跨天翻查；
2. 需要一个「该运行已结束，实时记录已随之清除」的终态画面（§8），语气是**正常收尾**，不是错误；
3. 「复制原文」是用户唯一的留档手段，所以**它要好找**（§9）。

---

## 2. 谁在什么时候打开它

三个真实场景，**信息优先级按这个顺序排**：

1. **「它们跑到哪了？」**（进行中，最高频）
   派出去 3 个子 AI，等了 5 分钟没动静。想知道：谁还在跑、跑了多久、正在写什么、有没有卡住。
   → 需要：**实时**、一屏看全、正在跑的最醒目。

2. **「它到底答了什么？」**（复盘，在主 agent 还开着的时候）
   一个子 AI 说"改完了"，但结果不对。想回去看：我当时怎么问的、它原话是怎么说的。
   → 需要：**按轮次翻**、输入输出都是原文。

3. **「有没有漏掉的？」**（收尾自查）
   有的轮次跑完了但主 agent 从没来取结果（这是这套系统里最常见的一类事故）。想一眼看出哪些产出被晾着了。
   → 需要：**未取结果**要有显眼标记。

## 3. 页面结构：一个页面，左右分栏

```
┌────────────────┬──────────────────────────────────────┐
│  会话列表       │  选中会话的轮次（输入 / 输出）          │
│  （常驻）       │                                      │
└────────────────┴──────────────────────────────────────┘
```

窗口变窄时可退化为上下。**没有第二个页面**。

## 4. 左栏：会话列表

这是场景 1 的主视图。**一屏之内要能回答"谁还在跑、谁出事了"。**

每个会话卡片必须表达（按重要性排）：

1. **状态**——见 §5，这是全页最重要的视觉信号
2. **是哪个引擎 + 什么模型**——`Codex / gpt-5.6-sol-high`、`Claude Code / 默认`、`Kimi Code / kimi-code/k3`
3. **能不能改文件**——见 §4.1，**不是简单两档**
4. **名字或编号**——会话可能有别名（`reviewer-1`、`impl-a`）；没有别名时是自动编号（形如 `codex-mfx8q2-a7c319`，很难读，**列表里要缩短**）
5. **轮次数、已跑多久、最后活动时间**
6. **正在跑时**：当前预览长度 + 正在写的最后一小段（约 400 字，滚动更新）——这是"还在动 vs 卡住"最直接的判据
7. **异常标记**：上一轮报错 / 有未取结果的轮次

**排序**：正在跑 → 有异常 → 空闲 → 已关闭。次级按最后活动时间倒序。

**数量**：常见 1~4 个，圆桌/循环类任务 5~12 个，极端 20+。**卡片要能在 12 个时仍然一屏可扫**——不要设计成占半屏的大卡。

### 4.1 「只读」不能当安全承诺（重要）

每个会话有一个权限档：`只读` 或 `可写`。**但"只读"的强度因引擎而异，这个差别必须在 UI 上表达出来**，否则会制造错误的安全感。

| 展示 | 含义 | 哪些引擎 |
|---|---|---|
| **可写** | 明确授权改文件 | 全部（用户显式选了写档时） |
| **只读（强制）** | 操作系统级沙箱拦截，**真的写不了盘** | 只有 Codex 的只读档 |
| **只读（约定）** | 它**仍然有能力写盘**，只是被要求不要写 | Oh My Pi / Claude Code / Cursor / Kimi 的只读档 |

**为什么必须区分**：如果页面上只写"只读"，用户会以为这个子 AI 不可能动他的文件。而五个引擎里有四个的"只读"只是一句约束，不是一道墙——它跑的 shell 命令照样能写盘。

设计上：三档要能一眼区分；**「只读（约定）」不应该用让人放松的绿色**——它比"可写"轻，但不是"安全"。

## 5. 状态语言（必须照抄，不要自创）

系统里有**两个正交的维度**，页面要合成一个人能懂的说法。这是本页面最容易设计错的地方。

**维度一：此刻在干什么**——`starting`(正在启动) / `running`(正在跑) / `idle`(空闲) / `failed`(上一轮失败) / `closed`(已关闭)
**维度二：还能不能用**——`healthy`(好的) / `degraded`(还能用但上轮出错) / `dead`(用不了了)

**推荐合成四档（原型里就用这四个，配四种颜色）：**

| 展示 | 条件 | 语气 |
|---|---|---|
| 🟢 **进行中** | `starting` / `running` | 活跃、有动感（可以有呼吸/流动效果） |
| ⚪ **空闲** | `idle` + healthy | 安静、待命 |
| 🟠 **有问题** | `degraded`，或 `failed` 但还能复用 | 警示但不是终结 |
| ⚫ **已结束** | `closed` / `dead` | 灰、退居次要，但**不能隐藏**（复盘要看） |

⚠️ **一个反直觉的坑，务必不要"优化"掉：** 有两个引擎（Cursor / Kimi）在两轮之间**不占任何进程**，但会话完全健康、随时可以继续。所以**"没有进程"不等于"死了"**——不要设计任何"有无 PID / 有无进程"的指示，也不要用它来推断存活。存活只看上面那四档。

## 6. 右栏：轮次详情（核心）

选中一个会话后，右栏是**这个会话的完整对话史，按轮次从上到下排列**。

### 6.1 顶部：会话信息条

引擎、模型、思考强度、读写档、工作区路径、创建时间、总轮次、上下文占用。

**上下文占用**是"这个子 AI 的记忆用了多少"，超过一定量它会变笨。需要一个轻量的量感表达（数字 + 程度指示）：

| 区间 | 含义 |
|---|---|
| < 300k | 正常 |
| 300k ~ 400k | 该收尾了 |
| ≥ 400k | 该换新会话了 |
| **未知** | **Cursor / Kimi 永远是这个值** |

⚠️ 「未知」必须显示成"未知 / 不适用"，**绝不能显示成 0 或空进度条**——那会让人以为"很空闲、很安全"，是反的。

### 6.2 每一轮：两段式

```
┌─ 第 3 轮 ·  用时 4分12秒  ·  ✅ 已完成  ·  ⚠️ 未取结果 ────────┐
│                                                              │
│  ▸ 输入                                     1,240 字  [复制] │
│    请审查 scripts/agent-bridge.mjs 里新增的…                  │
│    （默认收起到 6 行，点开看全文）                            │
│    ⚠️ 超长输入会被截断保存，此时必须显示                       │
│       「已截断 · 原始 12.3 MB / 保存 4 MB」，                  │
│       否则"复制原文"会把截断件当原文交出去                     │
│                                                              │
│  ▾ 输出                                8,932 字  [复制][原文] │
│    ┌────────────────────────────────────────────────────┐   │
│    │  渲染后的 Markdown 正文（默认展开）                  │   │
│    │  含代码块、列表、表格                                │   │
│    └────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

**只有输入和输出两段。** 页面**不显示**"它中间读了哪些文件、跑了什么命令"——那些内容不在这个页面的范围内，想看的人页面会给出一个**日志文件路径**让他自己去开。**这里没有一处会出现大段滚动的日志文本，不要为它留版面。**

**默认折叠**：输入收起到前几行（通常是主 agent 写的长指令，看个开头就知道是哪件事）；输出展开；**最后一轮两段全展开**。

### 6.3 每轮头部的两个标记

**① 结果，四档**（不是三档）：

| 展示 | 含义 |
|---|---|
| ✅ 完成 | 正常跑完 |
| ❌ 失败 | 报错、协议错误、进程意外退出、中断超时 |
| ⏹️ 被中断 | 有人明确叫停，且确实停下来了 |
| 🚫 **未收场** | 会话被关闭或整个程序退出，把这轮**从中间截断了**，连它到底成没成都不知道 |

第四档容易被漏掉，但它恰恰最该被看见——它代表**这轮的结果永远拿不到了**。

**② 正文有无，三档**：完整正文 / 只有片段（可能不完整）/ 无正文。

**③ ⚠️ 未取结果**（见 §2 场景 3）。

### 6.4 结果 × 正文 的组合矩阵（决定你要出几张图）

12 个格子里真实存在的只有一部分。**别每格都画，也别自己猜。**

| | 完整正文 | 只有片段 | 无正文 |
|---|---|---|---|
| ✅ 完成 | ✔ 绝大多数 | ▲ 少见（某引擎正文可能不全时如实降级） | ✖ |
| ❌ 失败 | ✖ | ▲ 有些引擎会留下已写的部分 | ✔ 常见 |
| ⏹️ 被中断 | ✖ | ▲ 部分引擎有 | ✔ 部分引擎（打断时什么都没留下） |
| 🚫 未收场 | ✖ | ▲ 偶尔 | ✔ 常见 |

**要出的图**：✅+完整（主态）、❌+无正文、⏹️/🚫+片段（带"可能不完整"标注）、🚫+无正文。四张覆盖绝大多数。

### 6.5 正在跑的那一轮：**实时预览** ≠ 正文

这是本页最需要拿捏的地方，也是**最容易设计错**的地方。请先接受一个技术事实：

> **子 AI 在写作过程中，已经写出来的内容是会被推翻重写的。**
> 它中途可能先输出一段阶段性结论，然后调用工具，再从头组织最终答案。
> 所以「过程中看到的文字」**不是**「最终答案的前半截」——五个引擎里有四个都会在收尾时整体替换。

因此运行中的那一轮**分成两个阶段**：

**阶段一：进行中 —— 实时预览区**

- 展示**当前正在写的一小段**（约 400 字的滚动窗口），每秒更新。
- **这是一个滚动的预览窗，不是在积累一份完整文稿**——不要设计成"文章越来越长、可以往上翻看全部"的样子。
- **必须有一句明确的状态标注**，例如「正在生成（内容可能被改写）」。
- 显示**当前预览长度**。⚠️ **这个数字会下降，也会长时间不动，都是正常的**。**不能用"数字在涨"当作"还活着"的判据**，也别做成只增不减的进度条。判断卡没卡，看的是**这段预览有没有在变**（内容 + 更新时间戳）。
- **「第 N 稿」徽章**：系统会告诉页面"刚才发生了一次重新组织"。请把它设计成一个明确的状态徽章，例如「**已重新组织答案（第 2 稿）**」——这比让人盯着一个莫名其妙缩水的字数好得多。
- 可以有轻微的"正在写入"指示，但**要克制**：这个页面可能开着几个小时。

**阶段二：完成 —— 正文落定**

- 预览区被**完整正文**替换（一次性出现，不是继续追加）。
- 这一刻的过渡需要设计：从"流动的预览"变成"稳定的文档"，让人明确知道**现在这份才是最终答案**。
- ⚠️ 这个过渡是**单向**的——一旦落定就不会再变回"正在生成"。

其余实时元素：没有"耗时"（还没结束），改显示"已进行 4分12秒"秒级走字；**自动滚到底**，用户一旦手动上滑就停止自动滚并给"回到底部"浮标。

## 7. 真实数据量级（原型请按这个填充，不要用 Lorem）

| 项 | 常见 | 极端 |
|---|---|---|
| 一个 run 的会话数 | 1~4 | 20+ |
| 一个会话的轮次 | 1~3 | 15+ |
| 单轮输入长度 | 200 ~ 3,000 字 | 100,000+ 字（会贴大段代码/规格） |
| 单轮输出长度 | 1,000 ~ 20,000 字 | **没有硬上限**，可以超过 40 万字 |
| 单轮耗时 | 30 秒 ~ 5 分钟 | 30 分钟 |
| 一个 run 的时长 | 十几分钟 | 十几小时 |

**内容形态**：中英混排、Markdown（标题/列表/表格）、大量代码块（含长行，需要**横向滚动**而不是撑破布局）、Windows 长路径、偶尔有 diff。

**超长输出的加载规格**（这是规格，不是建议）：正文**整份一次加载**；超过 8 MB 的部分不加载，改为显示前 8 MB + 一句提示 + 文件绝对路径供用户自己打开。所以**不需要设计"继续加载"分页交互**，但**需要考虑超长正文的滚动性能**（虚拟滚动或分段渲染由实现决定，版面上不体现）。

（Markdown 的代码块/表格样式可参考兄弟页面 `skills/agent-bridge-roundtable/viz/index.html`，可直接用浏览器打开看。）

## 8. 空态与异常态（都要出图）

| 情形 | 说明 |
|---|---|
| 一个会话都没有 | 主 agent 还没派活。给一句解释，不要空白页 |
| 会话开着但一轮都没发 | 常见（先开会话再派活）。轮次区要有"尚未发起任何轮次" |
| 会话**启动失败** | 引擎没装 / 模型名写错。**这类会话会作为一张"生下来就死了"的卡片出现在左栏**（有完整的引擎/模型/目录/权限信息），选中后右栏只有一条错误。要能显示，不能吞掉 |
| 轮次失败 / 被中断 / 未收场 | 见 §6.4 矩阵。⚠️ **不能承诺"总能看到半截输出"**——有的引擎被打断时什么都不留。无正文时给一句「这轮没有留下可查看的输出」，不要留空白框 |
| 未取结果 | 见 §2 场景 3，显眼但不惊悚的标记 |
| **运行已结束、记录已清除** | **必出图。** 主 agent 一关，这次 run 的全部内容立即消失。正在看的人会突然失去内容——需要交代清楚：「该运行已结束，实时记录已随之清除」。**语气是正常收尾，不是报错** |
| 记录不完整 | 系统写入出问题时会自报"本次记录不完整"。需要一个不打断阅读的提示条 |
| 服务断连 | 页面靠一条长连接接收实时更新。断了要提示 + 自动重连，**不要静默停止更新**。注意与上一条**区分**：断连是"我暂时看不到"，记录清除是"它已经没有了" |

## 9. 交互清单

**必须有：**
- 选中会话（左栏 → 右栏联动）
- 展开/收起：输入、输出
- **复制：输入原文、输出原文**（一键，带反馈）。⚠️ 这是用户**唯一的留档手段**（记录随主 agent 关闭而消失），不能藏在二级菜单里——每轮的输入/输出区都要有随手可点的复制
- 查看原文：跳到未渲染的纯文本
- 实时更新 + 自动滚动（含"用户上滑则暂停"）
- 会话列表筛选：至少能过滤「只看进行中」「只看有问题」
- **刷新恢复**：选中的会话、展开的轮次要能在刷新后回到原处（本地页面通常用 hash 路由，请在原型里体现 URL 变化）

**时间显示口径**（一个开十几小时的页面里这是真问题）：
- 列表/卡片上的"最后活动"用**相对时间**（"3 分钟前"）
- 轮次头部的开始/结束用**绝对时刻**（本地时区，`14:05:49`；跨天时补日期）
- 耗时用 `4分12秒` 这种可读形式

**加分：** 全局搜索（跨会话搜输入/输出）、折叠左栏、深浅色主题、键盘上下切换会话。

**明确不要：**
- ❌ **任何操作按钮**：不能在这里发消息、中断、关闭会话。这是只读观测台——控制权在主 agent 手里，页面上动手会让两边状态打架。
- ❌ 编辑/批注内容
- ❌ 登录、账号、多用户、权限
- ❌ 分享链接、导出报告
- ❌ 图表统计仪表盘（这不是分析工具）
- ❌ 历史运行列表 / 归档 / 按日期分组（记录是临时的，见 §1）

## 10. 技术与视觉约束

- **单个 HTML 文件，零外部依赖**：不能引 CDN 的字体、图标库、UI 框架。图标用内联 SVG 或 emoji，字体用系统栈。（原型可以随意做，但请知道**最终实现有这个约束**，别把设计压在某个特定字体/图标集上）
- **本地页面，桌面浏览器**，主流窗口宽度 1280~2560。不需要移动端适配，但窗口变窄时左右分栏应能退化为上下。
- 深色 / 浅色都要有（开发者常用深色）。
- 参考既有兄弟页面的视觉语言，最好能成一家人：`skills/agent-bridge-roundtable/viz/index.html`、`skills/agent-bridge-loop/viz/index.html`。
- 长时间开着不动（十几小时），**不要有持续动画/闪烁**；"正在跑"的动感要克制。

## 11. 附：字段字典（原型填充数据用）

| 字段 | 取值 |
|---|---|
| 引擎 | `omp`(Oh My Pi) / `codex`(Codex) / `claude`(Claude Code) / `cursor`(Cursor Agent) / `kimi`(Kimi Code) |
| 模型 | 自由字符串，如 `gpt-5.6-sol-high`、`anthropic/claude-opus-5`、`kimi-code/k3`；**可以为空**（用引擎默认） |

| 权限档 | `read` / `write`。⚠️ 展示按 §4.1 分三档：`可写` / `只读（强制）`（仅 codex 的 read）/ `只读（约定）`（其余四家的 read） |

| 健康 | `healthy` / `degraded` / `dead` |

| 上下文占用 | 整数 tokens 或 **未知**（Cursor/Kimi 恒为未知） |
