# 让用户能对已完成的委托会话追问 —— 可行性评估

**日期**：2026-08-02（当天按澄清后的需求重写过一次）
**需求**（用户澄清后的准确版本）：

> 每个通过 agent-bridge 派出去的 AI 都是独立进程。**我不是要插话或打断它们。**
> 我的诉求是：某个 AI 之前已经干完一个任务，它身上还留着那次的上下文，**我想基于那个上下文继续追问**。
> 它的回答同样能被主 agent 拿到。但在留在本地的记录里，要标出这一问一答**是主 agent 提的还是用户提的**。

**怎么做的这份评估**：三个 AI 分头调研（技术可行性 / 产品语义 / 安全风险），结论各自独立得出、再交叉核对；文中每条事实都回到代码验证过。

---

## 一句话结论

**能做，比想象的小。工期一周左右，但有一件事必须先做：给那个网页装锁。**

最初评估时我们把需求理解成「插话 / 当场纠正正在干活的 AI」，那个版本很难做（底层不支持并发，最想插话的那一刻恰好插不进去）。**你澄清之后，那些难点全部不适用了**——只对**已经闲下来**的会话追问，正是底层支持得最好的情况。

而且有一个现成的便宜可捡：**你要的那个「谁提的」标记，位置已经存在了。**

---

## 一、先说清楚今天已经有什么

打个比方：主 agent 是项目经理，它派出去的每个 AI 是一个临时工，各住一间独立的屋子。观测台是墙上开的一扇**只能看的窗**。

你现在想要的是：**某个临时工把活干完了、闲着，你隔着窗问他一句「刚才那个事，再帮我看看 X」。**

好消息有三条：

**1. 一轮一对文件，本来就分开存着。**
观测台的归档目录里是这样的：

```
turns/<会话>/t1.in.md   ← 第 1 轮问了什么
turns/<会话>/t1.out.md  ← 第 1 轮答了什么
turns/<会话>/t2.in.md   ← 第 2 轮问了什么
turns/<会话>/t2.out.md  ← 第 2 轮答了什么
...
```

不是「只留最后一轮」，是**每一轮都留**。你说的「写在本地的文件里的内容」，指的就是这些。

**2. 每一轮上已经有一个「谁发的」字段了。**
叫 `source`，现在两个取值：开场白 / 后续消息。**你要的标记，加第三个取值就行**——落点、格式、读取方全是现成的。

**3. 追问本身，底层完全支持。**
会话是长期活着的，主 agent 平时就是这么追问的（同一个会话发第二条、第三条消息）。你要的只是把这个能力从「只有主 agent 能用」开放给页面。

---

## 二、还剩下什么真问题

原来的三个难点，澄清之后只剩一个半。

### ❌ 不再是问题：「最想插话时插不进去」

底层五个引擎都不接受并发（正在干活时喊话会被当场拒绝）。这原本是最大的痛点——因为「它跑偏了我要拉回来」恰好落在做不到的那格。

**你明确说了不要插话、不要打断，只对闲着的会话追问。那这条完全不适用。**

### ⚠️ 缩小了，但还在：「主 agent 可能拿错答案」

底层给主 agent 取件的那个通道，**每个会话只有一份「最新答案」**，新的会盖掉旧的。

危险的情况**只有一种**：

> 临时工干完了主 agent 的活 → **主 agent 还没来取** → 你这时追问一句 → 新答案把旧的盖掉 → 主 agent 来取，拿到的是**你那句的答案**，却以为是自己任务的成果

注意这跟归档无关——归档里两轮都好好存着。坏的是**主 agent 取件的那条通道**。

**这个好挡，而且判据现成**：底层本来就有一本「谁还欠着没取」的账（每次主 agent 调工具时都会提醒它「你还欠一笔」）。

> **规则：这个会话有没取走的结果时，页面上不让发。** 并说清原因：「主 agent 还没来取上一轮的结果，现在发会把它弄丢。」

在你描述的场景里，这条几乎不会挡到你——主 agent 通常是**干完、取了结果、汇报给你之后**你才想追问的。

### 🔴 完全不变：那个网页今天没有锁

跟需求形状无关，跟「页面能不能发指令」有关。

今天这个页面：只在你自己电脑上开着（外网访问不到），但**不验身份、不查请求从哪来**，文档里还教人用固定端口。

今天没事，因为**它只能读**。最坏是同机别的程序能看到你派出去的活的内容。

**一旦它能发指令，性质就变了**：任何一个能让你浏览器发出请求的网页，都能往你的 AI 那儿塞一句话让它干活。你在别的标签页随便打开一个网站，它就能悄悄下指令，而你什么都看不到。

有人会想：那只让「只读」的会话能发不就行了？**不行。** 五个引擎里只有一个是被系统真正锁死的，其余四个的「只读」是**靠提示词压着的**——照样能执行命令、能写盘。

**这一条是「做不做得成」的分界线，不是「做得好不好」的问题。**

---

## 三、要做的事（就这四件）

**1. 装锁**（必须，且必须在页面能发出任何指令之前）
一次性凭证 + 校验请求来源 + 限制请求类型。三样缺一不可。

**2. 页面能对空闲会话发消息**
走底层现成的发送通道，一行新逻辑都不要另写——那样闸门、记账、归档全部白送。

**3. 加第三个「谁发的」取值**
落在已有的 `source` 字段上。归档里每一轮自动带上，页面上两种来源分开显示。

**4. 主 agent 那一侧看得见**
它取件时要能看出「这一轮是用户问的，不是我的任务」。现成的通道就能挂（那本「你还欠着」的账，每次调工具都会带给它）。

**加一道闸**：会话有没取走的结果时不让发（上面第二节那条）。

> **✅ 已拍板（2026-08-02，用户）：禁掉，不是提示。**
> 有未取走的结果时，页面上的发送就是不可用的，并说清原因——不是弹个「确定要继续吗」让人点过去。
> 理由：放开的话不是必然出错，是**偶尔**出错，而出错时主 agent 拿到的替代品**看起来完全正常**，
> 没有任何征兆能揭穿。这类「说出来的话对其中一件事必然是假的」的问题，本仓踩过好几次，
> 一次比一次贵。一道会被人点过去的提示，等于没有这道闸。

## 四、你没提到、但会自己冒出来的几件事

按「不做就是坏的」和「不做只是缺」分开。

### 必须（不做的话这功能是坏的，不是缺的）

**发之前就知道能不能发。** 会话忙着、已经关了、或者有没取走的结果——这三种情况下发送应该是灰的，并用人话说清为什么。不做的话你点下去收到一句英文报错，分不清是自己弄错了还是页面坏了。

**主 agent 要知道「用户追问过」这件事本身。** 你那句话进了临时工的脑子，之后每一轮它都带着。主 agent 如果不知道，它会看到临时工突然改主意却完全无法解释——**它在按一个自己看不见的东西做判断**，这是最难查的一类问题。

**发出去之后看得见在跑、看得见答案。** 这不是新功能，是「发送」这个动作的完成态。页面已有的东西够用，基本白捡。

### 该有

**归档里两种来源分开显示。** 这个页面的立身之本就是「这次到底发生了什么」，混着显示等于记录不诚实。回头查「它为什么这么答」，第一个要问的就是「这句是谁说的」。

**发送框要能看到这个会话之前聊过什么。** 你是「基于上下文追问」，那你得先看得到上下文。页面现在已经能逐轮翻，把发送框放在那个位置就行。

### 明确不做

**打断、关闭会话、改权限。** 你说了不要打断；关会话会把成果删掉；权限是开会话那一刻定死的，中途改不了——更要紧的是，它会把你亲手授权过的边界，变成从一个网页上就能翻的边界。

**「撤回」。** 话进了对方脑子就撤不回来。别做一个假按钮。

**「引用它的原话回复」。** 听起来自然，但它是把 AI 写出来的内容塞回页面结构里最自然的理由，而页面现在的转义处理不全，这一步会打开一个新的攻击面。

**多个标签页同时对同一个会话说话。** 页面不知道谁是谁，只会造出新的抢话问题。

## 五、几件要提前知道的事

**1. 你追问的内容会永久留在那个 AI 的上下文里。** 主 agent 之后再用这个会话派活，它带着你那段对话。通常这正是你要的（你就是想用那个上下文），但主 agent 得知道。

**2. 上下文额度是共用的。** 主 agent 靠「用了多少」来决定什么时候关掉旧会话开新的。你追问也吃这个额度，而它看不出来为什么突然涨了。小问题，但会偏。

**3. 用 cursor 派出去的会话要留神。** 它的内容会进 Cursor 云端而且删不掉，同一目录下之后新开的会话还能读到。今天说话的只有主 agent、内容是任务；开放给你之后，人随口打的字更容易带私事。

**4. 归档目录里会多出你手打的内容。** 现在观测台默认开着，当初算这笔账时算的是「你电脑上会存着所有派出去的活的内容」。加了对话之后还会存你自己打的字。这笔账要重新算一次。

**5. 有一个现成的小毛病要顺手修。** 那个 `source` 字段的「开场白」这一档，**在实际运行里从来没有真正出现过**——开会话时调用的地方漏了传这个参数，所以所有轮次都被标成了「后续消息」。现有的检查只查「值合不合法」，查不出「有一档从来没出现过」。**新加一档如果不配一条真跑的用例，会原样复制这个毛病。**

## 六、工期与代价

| | 量级 |
|---|---|
| 装锁 | 2~3 天 · **不可省** |
| 页面发送 + 标记 + 闸门 | 3~4 天 |
| 规范文档 + 检查程序 | 1~2 天（按规矩检查程序必须是独立写的第二份实现） |
| **合计** | **约一周** |

比最初评估的「1~2 周起、还要先拍板七条冲突」小了一个量级。原因就一条：**你不要插话，只要对闲着的会话追问**——那些冲突大半是「插话」带来的。

## 七、最后的判断

**该做，范围清楚，工期可控，开工前该定的都定了。**

唯一那个待定项已经拍板：**有未取走的结果时，页面上直接禁掉发送**（见第三节）。

所以下一步就是动手，没有别的前置条件。开工顺序不能变：

1. **先装锁** —— 在页面能发出任何一条指令之前。这不是「先做安全再做功能」的老生常谈，
   是因为「页面能发指令」这件事一旦上线，锁没装就是一个对本机敞开的后门，补锁时它已经在跑了。
2. 再做发送 + 标记 + 那道闸
3. 最后是规范文档与检查程序

**一句更正**：上一版评估里我建议「先给用户开一间自己的屋子」。按你现在的澄清，**那条不解决你的问题**——你要的正是复用已有的上下文，新开一间屋子就是重新开始。这条作废。
