> 读这份文档不需要任何 agent / AI 工程背景。§2 是术语表，看完就够。

> **这一版（v14）改了什么**：①**「运行被中途掐断」整个改名为「未观测到正常收尾」**（§4.1 状态表、§8 标题与表格、§10 第 14/19 张图）——定义是"我们没看到它正常收尾"，**进程被强杀只是最常见的成因，不是定义**（报信的两条通道同时坏掉时，它其实可能有序收了场）。②新增**「有界摘要」组件**（§6.4）：长文本超限时不是一段完整原文，而是"头 + 尾 + 省略了多少 + 总量 + 指纹"，**结尾必须显示**（根因常在最后一行），绝不能出现 `[object Object]` 或"只给开头且不说省略过"。③**「服务自灭倒计时」删掉**（§8）：只要你开着页面它就不退出，**根本没有"还剩多少秒"可显示**，改成一句静态说明。④端口 7345 不再写死（被占会自动换）。

## 0. 一句话

**一个只读的实时观测台，用来看"一批 AI 分头干活"这件事此刻进行到哪一步、每个环节喂进去了什么、吐出来了什么、改了什么。**

类比：像 CI 流水线的执行页，但每个"步骤"不是一条命令，而是**一个 AI 在读代码、写分析、或者真的改文件**；步骤之间的连线不总是明确的，有的靠推断（§5）。

## 1. 用户、场景、要回答的问题

**唯一用户**：发起这次运行的工程师（本机打开**启动器打印出来的那个 `localhost` 地址**，默认端口 7345；⚠️ **端口被占时会自动换一个**，所以文案与说明里别把 7345 写死。无多人、无权限、无登录）。

| 场景 | 心态 | 关键诉求 |
|---|---|---|
| **运行中盯着看**（5～60 分钟） | 焦虑、频繁瞥一眼 | 一眼看出"还在动吗、卡在哪、要不要现在打断" |
| **跑完了复盘** | 冷静、逐个点开 | 找到某个环节的输入输出，判断它干得对不对 |

**页面必须能在 3 秒内回答的六个问题**：

1. 这次跑了哪些环节？总共几个？
2. 此刻哪些**在跑**、哪些**在排队**、哪些完了、哪些挂了？
3. 环节之间是什么关系（谁在谁之后、哪些并行）？
4. 某个环节，**喂给它的原话**是什么？
5. 某个环节，**它吐出来的东西**长什么样？被打回重做过的话，**两次分别**长什么样？
6. **改代码的环节，改了什么？改动现在在哪？**

## 2. 术语表

| 词 | 意思 | 设计上怎么理解 |
|---|---|---|
| **运行（run）** | 一次完整执行 | = 这个页面的全部内容，一页一个 run |
| **环节 / 节点（node）** | 一个 AI 干一件事 | 基本卡片单位。⚠️ **`id`（如 `audit-auth`）是逻辑名，可以重复**——同一次运行里允许把同一个环节重跑一遍，两次都要各自成卡。**页面的唯一键由技术方案给出（`nodeSeq`），不是 `id`**；拿 `id` 当 DOM/状态 key，第二次会覆盖掉第一次 |
| **引擎（agent）** | 干活的 AI 是哪家 | 五种：`codex` / `omp` / `claude` / `cursor` / `kimi`。**需要一眼区分**，因为"换个引擎复核"是这个工具存在的理由 |
| **输入（input）** | 喂给这个 AI 的完整原话 | 纯文本 / Markdown，200～5000 字 |
| **产出（artifact）** | 这个 AI 吐出来的完整答案 | Markdown，1000～50000 字。**改代码的环节也有产出**（它的工作报告） |
| **尝试（attempt）** | 一个环节最多跑 2 次 | 第一次输出不合格会被打回重说一次。**两次的输入输出都要能看** |
| **状态（status）** | 环节干得顺不顺 | 7 档，见 §4.2 |
| **复用（reused）** | 没真跑，直接用了上次的结果 | **正交标记，不是一种状态**，见 §4.3 |
| **依赖（deps）** | 环节之间的先后关系 | 三种可靠性，**必须视觉可区分**，见 §5 |
| **read 模式 / write 模式** | 这个环节有没有独立工作副本 | 见 §4B。**注意：这不是安全边界** |
| **改动结论（outcome）** | 改代码的环节到底交付了什么 | 三档，见 §4A |
| **独立工作副本** | write 环节各自的隔离目录 | 各改各的互不干扰；正常跑完就提交、目录删掉 |
| **分支 / 改动清单** | 改动的最终去处 | write 环节的交付物：一个分支名 + 一份文件改动清单 |

## 3. 页面结构

单页，无路由跳转：

```
┌───────────────────────────────────────────────────────────────┐
│ A 顶栏：运行概览 + 连接状态                        （常驻，细） │
├──────────────────────────────────┬────────────────────────────┤
│  B 主视图：环节全景               │  C 详情面板                │
│    ├ 图视图（默认）               │    点选环节后出现          │
│    └ 时间轴视图（切换）           │    未选中时收起            │
└──────────────────────────────────┴────────────────────────────┘
```

C 区可以是右侧抽屉或全屏叠层——由你判断，但**必须能与 B 区同时可见**。

## 4. 状态语义

### 4.1 运行阶段

| 阶段 | 含义 | 视觉 |
|---|---|---|
| **已发现** | 系统认下了这个环节，正在做本地准备 | 最弱，几乎只是占位 |
| **排队中** | **已进入本地队列，还没派给 AI**——同时能跑的环节数有上限（默认 4） | 安静、明显"还没开始"，**不能有动效** |
| **运行中** | **已拿到执行名额**——可能正在准备独立工作副本，也可能已经派给 AI 在跑 | **最高权重**，唯一有动效的状态 |
| 终态 | 见 4.2 | — |

> ⚠️ **早先的稿子把「排队中」写成"已经派了，但在等名额"——这是错的。** 排队发生在**联系 AI 之前**：排队中的环节**一个字都还没发出去**，那边什么都不知道。写成"已经派了"会让用户以为对面正在处理，从而误判"是不是卡住了要打断"。准确说法是**「已进入本地队列，尚未派给 AI」**。
>
> ⚠️ **「运行中」的口径要写清**：对改代码的环节，它拿到名额后**先要准备一份独立工作副本**（复制代码、建分支），这一段也算「运行中」，但此时**还没有联系 AI**。详情面板应能区分这两段，否则用户看到"运行中但一个字都没吐"会以为它挂了。
>
> ⚠️ **「排队中」不能省，也不能画得像「运行中」。** 扇出 8 个环节而名额只有 4 个时，一半的环节处于这个状态。50 个环节时可以有 **46 个同时排队**。v1 没有它——那意味着用户会看到"8 个里只有 4 个"，剩下的**凭空消失**。
>
> ⚠️ **排队中的环节没有在消耗自己的超时预算**——计时从拿到名额那刻才开始。所以**不要给排队中的环节显示倒计时或进度条**，那是在暗示一件不存在的事。排队时长本身要显示（它是"名额开太小了"的诊断信号）。

### 4.2 结局，七档

**语义差别很大，不能只靠颜色深浅区分**：

| 状态 | 含义 | 用户该做什么 | 视觉权重 |
|---|---|---|---|
| **ok** | 顺利跑完 | 点开看产出 | 低（成功是常态，不该抢注意力） |
| **contract_error** | 跑完了，但输出格式不合格 | 看它到底吐了什么 | 中 |
| **timeout** | 超时被打断 | 考虑加时间或拆任务 | 中 |
| **backend_failed** | 引擎明确报错 | 可以安全换个引擎重跑 | 高 |
| **被拒绝** | **还没开跑就被本地挡下了**（见下） | 看拒绝原因，通常是脚本或环境的问题 | 中 |
| **unknown** | **说不清它干没干完** | ⚠️ 停下来人工看，**绝不能自动重跑** | **最高** |
| **abandoned** | **没看到这个环节的结局**（本次运行**未观测到**正常收尾） | 见 §8——**现场往往还在** | **最高** |

**`unknown` 的特殊性要设计出来。** 它不是"一种失败"，是"我们不知道发生了什么"——在这套系统里它最贵，因为盲目重跑可能让同一件事做两遍。需要一个**不同于其它失败**的视觉语言（**不是更红，是更"警戒"**）。

#### ⚠️「被拒绝」必须与「失败」和「不明」都分开

有一类环节**根本没被派出去**：id 和别的环节撞了、代码仓库不干净、上次的结果对不上不能复用、独立工作副本建不起来。这时系统**当场停下并报错**，AI 那边一无所知——**没有花钱，也没有一个"结局不明"的任务在后台跑**。

⚠️ **绝不能把它显示成 `unknown` 或 `abandoned`**——那两档都在喊"停下、现场还在、别乱动"。**把利落的拒绝画成事故，用户下次就不信这套告警了。**

⚠️ **但也不能一律画成"无事发生"**——四种拒绝里有两种**可能已经有东西在那儿**了，页面必须按拒绝原因分开说：

| 挡在哪一步 | 页面说什么 | 有没有东西要管 |
|---|---|---|
| **撞 id** | 「这个名字被占着」 | ⚠️ **有**：占着它的可能是**另一个正在跑的进程**，也可能是上次异常退出留下的。**两种处置完全相反**（一个要等、一个要清），页面必须让用户知道要先分辨 |
| **仓库体检没过** | 「你的代码目录有没提交的改动」 | 无（是用户自己的工作区状态） |
| **复用校验没过** | 「上次的结果和这次对不上，不能拿来用」 | 无 |
| **建工作副本失败** | 「独立工作副本没建起来」 | ⚠️ **可能有**：常见原因就是"上次残留的工作副本/分支清不掉"，那东西**还在**；也可能是建到一半失败、自动清理也没成功 |

**所以「被拒绝」是一档中等权重的状态**：不需要 `unknown` 那种最高警戒，但**第一行和第四行必须给出"要去看什么"**，不能只丢一句"被拒绝了"。

### 4.3 「复用」是标记，不是状态

有的环节没真跑，直接用了上次的结果。它**仍然是一个成功的环节**（`ok`），只是多一个「复用」标记。

⚠️ **必须与真跑的成功明确区分**——否则用户会以为"这次验证过了"，而实际上这次什么都没验证。建议做成角标/徽章，而不是换颜色（换颜色会让它看起来像另一种结局）。

### 4.4 引擎标识

五种引擎需要稳定的视觉标记（色/字母/图形皆可），同一引擎在全页任何位置必须同一个标记。用户最常问的一句是"这个结论是哪家 AI 给的"。

## 4A. 改代码的环节：第二个状态维度

有的环节被授权改代码。它跑在一个**独立工作副本**里，除了照常吐一份工作报告，还额外交付**一批文件改动**。

> ⚠️ 措辞纠正：**不是"它交付的不是文字而是改动"**。它同样要交出一份文字产出（工作报告），**改动是额外多出来的一份交付物**。

所以这类环节有**两个正交的状态**，页面要表达的是**组合**：

- **状态**：这个 AI 跑得顺不顺（七档，§4.2）
- **改动结论**：改动最后**落到哪儿了**（三档，下表）

### 三档改动结论

| 结论 | 含义 | 页面必须给什么 |
|---|---|---|
| **已交付** | 改动已提交，进了一个分支 | 分支名 · 改动清单 · 清单入口 |
| **无改动** | 收尾检查时**没有检测到可提交的改动** | 一句陈述。**没有改动清单可看——不要留一个点了没反应的入口** |
| **交付状态不明** | 提交失败 / 检查失败 / 这个 AI 自己动了版本控制 | ⚠️ 见下 |

⚠️ **「已交付」不等于"有一批文件改动"。** 存在一种真实且合法的形态：**分支往前走了，但净改动是空的**（这个 AI 建了个空提交，或者改完又自己撤回了）。此时改动清单是**零项**、diff 是**空文件**，但结论确实是「已交付」。

页面必须能表达这一格，而且**不能退回去说"无改动"**——那是另一个结论，会让用户以为分支上什么都没有。建议文案：**「已交付，但这次提交没有净改动」**，仍然给出分支名与基线。

⚠️ **「无改动」的文案不能写成「它认为不需要改动」。** 系统**没有**"这个 AI 怎么想"这种信息——它只知道**收尾快照里没检测到可交付的改动**。写成"它认为"是替 AI 编造意图，用户会据此得出错误结论（比如"那就是不用改了"，而实际可能是它改错了地方、或者改的是被忽略的文件）。

建议文案：**「收尾检查未发现可交付的改动」**。

### 两个"说不清"必须用不同的话说

页面上会出现两种不同的"不明"，**绝不能用同一句话**：

| | 含义 | 建议文案 |
|---|---|---|
| 状态 = unknown | **执行结局**不明 | 「这个环节干没干完，说不清」 |
| 改动结论 = 交付状态不明 | **代码去向**不明 | 「改动有没有落到分支上，说不清」 |

### ⚠️「交付状态不明」＝ 现场被保留，必须最醒目

正常情况下 write 环节跑完会**删掉自己的工作副本**。结论是「交付状态不明」时，系统**刻意不删**那份副本，因为里面可能有还没进分支的代码。

页面必须给三样，缺一不可：

1. **工作副本的完整路径**（可一键复制）
2. **一句话说明为什么不明**
3. ⚠️ **明确警告：不要自动重跑。** 重跑可能让同一件事做两遍，或把那份还没保住的代码覆盖掉

> 这一档在视觉上要与「失败」区分：失败是"这事没成"；**交付状态不明是"结果不明，而且系统刻意保留了现场，等你去看"**。它需要的是**行动引导**，不是错误提示。

⚠️ **措辞注意**：这里说的是「**系统当时选择了保留**」，仍然不能写成「它现在还在磁盘上」——理由与下一节相同（那是一张收尾快照）。文案应是「**已为你保留，路径在此**」，让用户去核对，而不是替他断言现状。

### 「工作副本是否已清理」是独立的一栏

⚠️ **早先的稿子把"副本还在"和"交付状态不明"绑在一起，这是错的。**

**已交付**和**无改动**的环节**也可能**留着副本——比如系统没能确认后端已经停下（此时删掉副本 = 可能丢代码），或者 Windows 上文件被占着删不掉。

所以详情面板要**两栏分开**：

- **交付结论**：已交付 / 无改动 / 交付状态不明
- **工作副本**：已清理 / **收尾时未确认清理**（+ 路径）

⚠️ **措辞纠正：不要写「仍在磁盘上」。** 系统记下的是**收尾那一刻自己有没有确认删成功**，这是一张**快照**，不是实时事实——用户打开页面时那个目录可能早被别的东西清掉了。写成"仍在磁盘上"就是把快照当现状，用户点过去发现没有，会开始怀疑整页数据。

准确文案：**「收尾时未确认清理」**（+ 路径，标明"可去核对"）。

### 组合速查（决定要出几张图）

| 状态 | 改动结论 | 页面主要在说什么 |
|---|---|---|
| ok | 已交付 | ✅ 分支 + 改动清单（**主态**） |
| ok | 无改动 | ✅ 「收尾检查未发现可交付的改动」 |
| ok / 失败 | 已交付，但**副本未确认清理** | ⚠️ 提示可能可清理的残留 |
| **失败三档** | **已交付 / 无改动** | ❗ **代码在分支上，只是这次执行不合格**——绝不能因为"失败"就把分支藏起来 |
| **unknown** | **已交付 / 无改动** | ❗❗ **最高执行警戒 + 分支照常给**（见下） |
| unknown | 交付状态不明 | ⚠️ **现场保留 + 路径 + 别重跑**（**最高警戒**） |

⚠️ **「失败 + 已交付」是真实且重要的组合**：AI 确实把代码提交了，只是报告格式不合格或引擎中途报错。**改动是可用的**，页面必须照常给出分支与清单。

⚠️ **「unknown + 已交付」是早先的稿子漏掉的一整类，而且最容易被设计吞掉。** 它的意思是：**这次执行干没干完说不清，但代码确实已经好好地提交在分支上了**。三种真实成因——联系 AI 时返回的东西看不懂、确认任务是否已开始时返回的东西看不懂、或者最后写结果记录时写不下去。

这一格要**同时**给两样，缺一不可：

1. 最高级别的**执行警戒**（同 `unknown`：停下来人工看、别自动重跑）
2. **照常给出分支名与改动清单入口**

⚠️ **绝不能因为状态是 unknown 就把交付信息藏起来**——那会让用户以为代码没了，然后去重跑，而重跑恰恰可能把已经交付的东西覆盖掉。这一格**不必单独出图**，但必须折进现有的判别态里（见 §10 第 12 张）。

⚠️ 反过来，**「失败三档 + 交付状态不明」不存在**——系统一旦发现交付状态不明，就会把整个环节的状态改成 unknown（因为"失败"会被理解成"可以安全重跑"，而重跑会删掉保留的现场）。**别为这个组合出图。**

## 4B. 「read 模式」不是安全承诺

⚠️ **早先的稿子写「只读环节 = 没权限改文件」，这是错的，而且是危险的错。**

真实情况：五个引擎里**只有 Codex 的只读档是操作系统级硬拦截**。OMP / Claude 的 shell **能写盘**；Cursor / Kimi 甚至**原生写文件的工具都还在**，只是被提示词压着别用。

所以页面的措辞应当是：

| 展示 | 含义 |
|---|---|
| **read 模式 · 无独立工作副本** | 不打算改文件；**改了也没有隔离，会落在主目录** |
| **write 模式 · 独立工作副本** | 明确授权改文件，且有隔离 |

必要时补一句引擎差异：**「Codex 为系统级只读；其余引擎为约定只读」**。

**为什么必须这么写**：如果页面写"只读"，用户会以为这个环节**不可能**动他的文件。而实际上四种引擎的"只读"只是一句约束，不是一道墙。**而且这个页面也观测不到这类越界写入**——它只看得见 write 环节的正规交付物。

## 5. 依赖关系的三种可靠性

这套工具**故意不要求用户声明流程图**。所以环节之间的关系有三种来源：

| 等级 | 来源 | 可靠性 | 建议画法 |
|---|---|---|---|
| **显式声明（未经验证）** | 用户自己写了"B 依赖 A" | **只是用户的一句声明——系统既不校验也不据此调度** | 实线箭头 + tooltip「仅展示，不影响执行顺序」 |
| **推断的** | 系统发现 B 的输入里提到了 A 的产出文件 | **可能猜错、也可能漏掉** | 虚线箭头 + 可解释的提示 |
| **只有时间** | 只知道谁先谁后、谁和谁同时在跑 | 无因果 | **不画箭头**，退化为时间轴 |

⚠️ **第一档不能叫"确定"或"精确"**（早先的稿子的措辞）。用户完全可以声明"B 依赖 A"，却在代码里让两者同时开跑——**系统不会阻止，也不会检查**。把实线读成"系统保证过的顺序"是错的。

**因此**：如果时间轴显示 B 比 A 先结束，而用户又声明了 A→B，页面应该给一个**一致性提示**（「声明的先后与实际执行不符」）。这比假装那条边成立诚实得多。

**硬要求：实线和虚线不能长得差不多。** 把推断当事实展示，是这个页面最容易造成的误导——用户会据此判断"这个结论是基于那个结论的"，而那可能根本不成立。虚线需要可点击/悬浮的解释（"根据输入里出现 `nodes/audit-auth.md` 推断"）。

### ⚠️ 排队会伪造出"先后关系"

因为同时能跑的环节数有上限，**B 在 A 之后跑，很可能只是因为没名额了，跟依赖毫无关系**。所以在**只有时间**那一档：

- 时间轴上**必须把"排队等待"和"真正在跑"画成两段**（如浅色前导条 + 实色主体条），否则用户会把等待读成执行
- **绝不要**把纯时间先后渲染成任何形式的箭头

**主视图两个视图，可切换**：图视图（默认，有边时画图）· 时间轴视图（**完全没有依赖信息时自动落到这个视图**——此时图视图会退化成一堆孤立方块）。

## 6. 详情面板

### 6.1 事实条（一屏内不用滚）

环节 id · 引擎标记 · 型号 · 强度 · 状态 · **复用标记**（若有）· **排队时长** · 执行耗时 · 产出字数 · 上下文占用 · **模式（read / write，按 §4B 措辞）**

> ⚠️ **复用来的环节，"执行耗时"是当初那次跑出来的，不是这次**。这次只做了一次几百毫秒的复用校验。所以复用卡片上必须写成「**原执行耗时**」——照直写"执行耗时 42 分钟"，会让人以为刚才真的又跑了 42 分钟。

> **上下文占用**在 `cursor` 和 `kimi` 上恒为"未知"——**不是 0**，设计上要能表达"未知"而不是显示成 0 或空进度条。

### 6.2 按尝试分段

最多 2 次。**只有 1 次时不要显示分段控件**（绝大多数是 1 次，不能让常态背上异常的 UI 成本）。

有 2 次时每段包含：输入（默认折叠）· 产出（默认展开，渲染后的 Markdown）· 打回原因（仅第一段）。

⚠️ **两次的输入是不同的**（第二次是"上次被打回的原因 + 纠正要求"拼出来的），**两次都要能看到各自的原文**。

⚠️ **有一个明确的例外，必须设计**：如果这个环节是**复用**来的，而**当初那次运行没有开可视化**，那么第二次的输入原文**在磁盘上根本不存在**（当时只留了指纹）。这时页面要显示「**原运行未归档输入原文，仅保留指纹**」+ 那串指纹。

**绝不能因此去"还原"一份看起来对的输入**——除非系统能用指纹逐字节验证它就是当初那份（技术方案里定死了这条规则）。**没验证过的还原就是伪造历史**，而这一段恰恰是审计价值最高的地方（"当初为什么被打回"）。

### 6.3 产出的呈现

- **渲染 Markdown**，不是显示源码
- **超长代码块 / 日志块默认折叠**，给出"展开（约 N 行）"
- 提供 **「看原文」** 切换 —— ⚠️ **硬约束：产出文件是审计原件，页面只能渲染、绝不能改写**
- 长内容需要**目录/锚点**或至少一个"回到顶部"

### 6.4 运行中的环节

6.2 的位置改为**实时进度**：已产出字数（持续增长）· **正在吐的文字末尾**（约 240 字的滚动尾巴，判断"还在动 vs 卡死"最直接的证据）· 最近一条生命周期事件。

### 6.5 出问题时

额外给：**错误详情** · 诊断信息列表 · "现场"文件入口（会话日志等）。

⚠️ **「错误详情」不保证是一段完整原文**：技术方案给长文本设了上限，**超限的会变成一份"有界摘要"**——只保留**开头一段 + 结尾一段**，中间省略。**结尾必须显示**，因为报错的根因常常在最后一行。

**所以要设计一个统一的"有界摘要"组件**，凡是长文本字段（错误详情、被打回的原因等）都可能用到它，要素五个：

| 要素 | 为什么 |
|---|---|
| 开头一段 | 看得到上下文 |
| **结尾一段** | **根因常在最后一行**，只给开头等于把最有用的丢了 |
| 中间省略了多少字节 | 让人知道自己没看到多少 |
| 总字节数 | 判断值不值得去翻原件 |
| 内容指纹 | 页面上这段与真实那段可对证 |

⚠️ **绝不能出现的两种做法**：把这个对象直接塞进文本里（页面上出现 `[object Object]`），或者只显示开头、**不告诉用户中间被省略过**。

### 6.6 每一个"可点开的东西"有四种基础态，外加两种派生态（**统一规则，全页通用**）

页面上凡是能点开看的东西——输入原文、角色设定、每一轮的产出、完整回执、改动详情、现场文件——**都不是"有"或"没有"两种**。**四种基础态由数据直接给出**，另有**两种派生态**由页面在别处的信息里推出来（见本节末尾两条）。**六种都必须长得不一样**：

| 基础态 | 含义 | 页面必须怎么做 |
|---|---|---|
| **有** | 记录下来了 | 可点击 |
| **不适用** | **本来就不该有**（没设角色、只读环节没有改动、正常收场没有现场） | 要么整块不显示，要么显示"不适用"——**但绝不能显示成一个点不开的按钮** |
| **⚠️ 拿不到** | **页面期望提供这项资产，但当前提供不了** | **必须显式说出来**（"这一项现在打不开：<原因>"） |
| **等待中** | 环节还在跑，这一项还没产生 | 占位，别显示成"没有" |

⚠️ **"拿不到"不等于"出了错"**：早先的稿子把它定义成"本该有，但记录时失败了"，可它底下的原因里有一条是**"当初那次运行没开可视化，所以只留了指纹"**——那是**用户自己的选择、完全正常**，硬说成"失败"就是在污蔑一次正确运行。所以这一档的准确含义只有一句：**页面想给你打开，但打不开**；至于为什么打不开，**由原因文案分辨**，其中一部分是故障、一部分不是。

⚠️ **第三种绝不能被静默隐藏。** 把"拿不到"画成和"不适用"一样（或者干脆不显示），就等于告诉用户"这东西本来就没有"——而实际上**系统本来是能给你看的**（要么它出了故障，要么当初就只留了指纹）。整套设计花了很大力气把这两件事分开，页面一含糊就前功尽弃。

⚠️ **还有第五种情况要单独说**：显示为「有」、但点开发现文件已经不在了。这时的正确文案是「**记录时它在，现在取不到了**」——**不能改口说"不适用"**。文件可能是被后来的清理删掉的，这与"本来就没有"是两件事。

⚠️ **第六种，也是最容易被漏的：记录断了，所以这一项**连状态都不知道**。**

如果记录是在这一项产生**之前**坏掉的，那么系统**既不能说它不适用**（不知道适不适用），**也不能说它没记下来**（不知道有没有尝试过）；环节都结束了，更不能一直显示"等待中"。

正确文案是「**记录从某处起不完整，这一项的状态未知**」。⚠️ **只要页面处于"记录损坏"状态，这一条就要盖过前面五种的推断**——否则页面会拿"我没看到"去推"它本来就没有"，那正是这份文档从头到尾在防的事。

⚠️ **「拿不到」必须给原因**，目前要各自有文案的有这几种：归档目录没建起来 / 这一项写盘失败 / 源头就没有可拷的东西 / 拷下来了但算不出指纹 / **当初那次运行没开可视化所以只留了指纹**（⚠️ **这一种不是故障**，文案里不能带任何"失败"的意味，措辞要中性到用户看完不会想去查问题）。

⚠️ **但这个清单是开放的，不是枚举。** 原因码只是一个字符串，**以后一定会加**。页面对**没见过的原因码**必须：照常渲染这一档、**把原始原因码原样显示出来**、给一句通用兜底文案——**不能崩，不能静默当成"不适用"，也不能把它归到上面某一条已知原因里**（归错比不认识更糟：用户会照着一条错误的解释去排查）。

（"现场"是个**目录**，里面三样东西——会话日志 / 回答原文 / 状态快照——**各自**有上面四种状态，很常见的情况是只拿到其中一两样。所以现场那一块要列三行，而不是给一个"打开现场"的总入口。）

### 6.7 改代码的环节：改动区块

read 环节没有这一节。按 §4A 三档分别呈现：

**已交付**——

- **分支名**（可复制）
- **改动清单**：每项是 **变更类型 + 路径**（新增 / 修改 / 删除 / 重命名；重命名显示为 `旧路径 → 新路径`）。典型 1～20 项，极端 100+，**要能滚动且不撑破布局**
- **改动详情入口**：点开看完整 diff。可能**很大**，按 §7 的超长内容策略处理
- **基线**：这份改动基于哪个版本（一个短哈希即可）

⚠️ **改动清单可能是零项**（见 §4A 的空提交形态）——此时**仍然要显示分支与基线**，并明说"这次提交没有净改动"，**不要**退化成「无改动」那套文案。

**无改动**——一句陈述（措辞见 §4A），**不要渲染空清单或空 diff**。

**交付状态不明**——路径（可复制）+ 原因 + 「不要自动重跑」。**这一块的视觉权重应高于同页任何其它内容。**

**外加一栏（三档都有）**：**工作副本** = 已清理 / **收尾时未确认清理**（+ 路径）。

## 8. 必须设计的非常态

| 情况 | 何时出现 | 需要 |
|---|---|---|
| **空态** | 页面开在脚本启动前 | "等待运行开始"，不是空白页 |
| **加载/回放** | 刚连上，正在回放历史 | 短暂的骨架态 |
| **断线** | 服务停了，**或者数据太快、服务端主动把这个页面断开让它重连** | 明确的"连接已断开"，**不要静默停止更新**。⚠️ **不能一律写成"服务停了"**：技术方案规定，当一个页面消费得太慢、积压超过上限时，服务端会**主动断开并期待它重连**（这比静默丢事件好）。重连后是一次完整回放，页面**不该**因此显示成故障，措辞要能覆盖"正在重连" |
| **运行已结束** | 正常收场 | 顶栏明确"已结束 + 汇总计数"；页面仍完全可浏览 |
| **⚠️ 未观测到正常收尾** | **最常见的成因**是用户按了 Ctrl-C / 进程被杀（但**成因不等于定义**，见下） | **常见情况，不是边缘情况**——见下 |
| **⚠️ 观测记录损坏** | 记录本身写不下去了（磁盘满、IO 错） | **必须单列，见下** |
| **历史回放不完整** | ⚠️ **不是**"打开得晚 / 刷新过 / 断线久"——那些现在**一定是完整的**（技术方案改成了从文件完整回放）。只有**读历史这一侧真的出错**才会发生：记录文件读不回来 / 中途被删被截断 / 读到坏行 | 若发生，页面要整体标明，**不能把"没回放到"显示成"本来就没有"**。⚠️ 也**不能**把它显示成「未观测到正常收尾」——那是关于任务的结论，而这里出问题的只是**我们读历史的这一侧**，任务很可能好好地在跑 |
| **服务会自己退出** | 运行结束、**且最后一个页面被关掉** 60 秒后 | ⚠️ **不要做倒计时**——只要你还开着这个页面，它就不会退出，**根本没有一个"还剩多少秒"可以显示**。改成一句静态说明：「**关掉最后一个页面后，服务将在 60 秒后退出**」 |
| **零依赖信息** | 用户没声明也推断不出 | 自动切时间轴 + 一句解释 |

### ⚠️「未观测到正常收尾」

技术事实：脚本被强行终止时**来不及写下"我结束了"**。页面若傻等那条记录，会**永远显示"运行中"**。所以页面会自己发现"干活的那个进程已经不在了"，此时：

1. 顶栏明确「**未观测到正常收尾**」——与「已结束」**不是一回事**，不能共用同一个视觉
2. 把还停在**已发现 / 排队中 / 运行中**的环节，统一标成 **`abandoned`**

> ⚠️ **这一档的定义是"我们没看到它正常收尾"，不是"进程一定被杀了"**。绝大多数情况确实是强杀，但**报信的两条通道同时坏掉**时，它其实可能有序地收了场（见本节末尾"观测记录损坏"）。**成因可以写在解释里，但不能写进定义**——页面替系统下一个它没观测到的结论，正是这份文档从头到尾在防的事。
>
> ⚠️ **脚本自己有序地报错退出不属于这一档**：那种情况系统来得及写下"我结束了（失败）"，顶栏应显示「**已结束（失败）**」。两者**不能共用同一个视觉**：一个是"没人知道后面发生了什么"，另一个是"它把话说完了，只是结论是失败"。

### ⚠️「观测记录损坏」——第三种收场，不能并进上面两种

页面的记录**本身**可能写不下去（磁盘满、IO 错）。这时运行往往**照常跑完了**，只是从某一刻起没人记下来。

**三种收场必须是三种说法，不能共用视觉：**

| 顶栏 | 什么情况 |
|---|---|
| **已结束** | 正常收场，记录完整 |
| **未观测到正常收尾** | ⚠️ 措辞不能写死成"进程一定被强杀"：记录通道和控制通道**同时坏掉**时（少见但真实存在），运行其实可能有序地收了场，只是**两条报信的路都断了**。页面只能说"没看到它正常收尾" |
| **⚠️ 已结束，但观测记录从某处起损坏** / **⚠️ 观测记录损坏，且不知道后来怎么样了** | 记录坏了。**这两句还要再分开**——系统能分清"坏了之后仍然正常收了场"与"坏了之后连收没收场都不知道" |

⚠️ **最关键的一条**：记录从第 N 条起损坏时，页面要**整体标注「此后记录不完整」**，**绝不能把那些没有结局记录的环节逐个标成 `abandoned`**。

**它们很可能好好地跑完了，只是没人记下来。** 把一次记录故障摊派成十几个"环节事故"，是这个页面能造成的最严重的误导——用户会去逐个排查十几个根本没出问题的环节。

### ⚠️ `abandoned` 的文案：**不要说"结果永远拿不到了"**

**早先的稿子这句是事实错误**，对改代码的环节尤其错——它的**工作副本、分支、锁文件往往都还在**，缺的只是一份"权威的结束回执"。写成"永远拿不到了"会**诱导用户放弃一个其实可以恢复的现场**，这与 §4A 反复强调的"保留现场、别重跑"自相矛盾。

准确含义是「**没有看到这个环节的结局**」。⚠️ **早先的稿子分了三种，不够——真实是六种**，而且其中两种，早先那份给出的承诺**页面根本兑现不了**：

| 中断时停在 | 文案方向 | 页面给什么 |
|---|---|---|
| **已发现** | 「本地准备中，还没派出去」 | 无需额外信息 |
| 排队中 | 「在等名额，**一个字都还没发给 AI**」 | 无需额外信息 |
| 运行中（read） | 「执行结果不明」 | ⚠️ **只列确实存在的现场文件；一个都没有就明说「未捕获现场」** |
| **运行中（write，还没开始建工作副本）** | 「正在做准备检查，**还没开始建，不会有工作副本**」 | **明确告诉用户不用去找** |
| **运行中（write，正在建、未确认建成）** | 「**可能已经开始建工作副本，位置未确认**」 | ⚠️ 给出**预定位置**，但必须标「未确认，可能不存在」 |
| **运行中（write，工作副本已确认建成）** | 「**执行与代码去向都不明；工作副本已建成**」 | ⚠️ **路径 + 分支名 + 「禁止自动重跑」** |

⚠️ **第三种：现场文件不保证存在。** 系统只有在**有序收场**时才会把会话日志等现场文件抢救出来；被强杀时那一步根本没机会跑。所以早先那句无条件的"现场文件入口"是空头支票——**页面必须能表达"这次什么现场都没留下"，而不是给一个点了 404 的入口**。

⚠️ **后三种必须两两分开，这是一处关键区分。** 改代码的环节拿到名额后，要先做几步检查、再建一份独立工作副本，这中间有两段窗口，**它们的正确答案彼此相反**：

- 第四种：**明确说"没有"**（这时创建动作压根还没开始）
- 第五种：只能说「**预定位置在这里，去看看有没有**」
- 第六种：才有资格说「**它确实在那儿**」

**把第四种写成第五种的语气，就是让用户去找一个可以证明不存在的目录**；反过来把第五种写成第四种，则是让他放弃一个可能真的存在、里面可能有代码的目录。**两个方向都是错的，而且都是同一个代价**：他扑空一次之后，第六种那句"它确实在那儿"就不再有人信——而那句正是整套设计里最不能被怀疑的一句话。

## 9. 交互清单

**必须有**：选中环节（B↔C 联动）· 展开/收起（输入、产出、改动清单）· **复制**（输入原文、产出原文、分支名、工作副本路径）· 「看原文」切换 · 实时更新 · 视图切换（图 ↔ 时间轴）· 排队区折叠。

**明确不要做**：

- ❌ **任何操作按钮**——不能暂停、重跑、改参数、关环节，**也不能合并分支**。这是只读观测台，任何写操作都可能与正在跑的进程打架
- ❌ 登录 / 权限 / 多用户 / 分享链接
- ❌ 多次运行的历史列表、跨运行对比
- ❌ 移动端适配（本机开发工具，桌面 1440 / 1920 两档即可）
- ❌ 改写或"美化"产出文本本身（只渲染，见 6.3）

## 10. 交付与参考

**交付**（桌面 1440 与 1920 两档）。**不必凑固定张数，但下面这些判别态必须覆盖**：

**常规**
1. 运行中（有并行、有运行中、**有排队**）
2. 已结束（含 1 个失败 1 个 unknown）
3. 详情面板 —— 单次尝试
4. 详情面板 —— 两次尝试（**两次输入各不相同**）
5. 时间轴视图（**排队段与执行段可区分**）
6. 空态
7. 断线态

**判别态（都是容易被设计漏掉、又最容易误导的）**
8. write · **已交付**（分支 + 改动清单）
9. write · **无改动**（措辞按 §4A，**不留空入口**）
10. write · **交付状态不明 / 现场保留**（最高警戒）
11. write · **已交付但工作副本收尾时未确认清理**（措辞按 §4A，**不写"仍在磁盘上"**）
12. **执行不合格 / 说不清 + 已交付**（同一张图证明两件事：`失败 + 已交付` 与 **`unknown + 已交付`** 都必须照常给出分支）
13. **复用**（证明它不伪装成普通成功）
14. **未观测到正常收尾**，同图含**三个** write 的 `abandoned`：「已确认建成」/「位置未确认」/「还没开始建」（证明三者语气各不相同，见 §8），外加一个**现场什么都没留下**的 read 环节，**再加停在「已发现」与「排队中」的各一个**（证明这两种的文案是"大概率什么都没发生"，不该和上面几种一样刺眼）
15. **一张同时含"声明边 + 推断边"的图**（证明两者视觉可区分）
16. **规模压力态**：50 节点 / 46 排队
17. **被拒绝**（§4.2）：同一张画板里放**两种**——「撞 id」与「建工作副本失败」。既要证明它**不长得像**事故，也要证明这两种给出的**处置提示不一样**（一个要先分辨是不是有人在跑，一个要去看残留）
18. **已交付但净改动为零**（§4A）：证明它**不退化成**「无改动」
19. **观测记录损坏**（§8）：**两个变体都要有**（同一张图或两张皆可）——①「已结束，但记录从某处起损坏」；②「记录损坏，且不知道后来怎样」。证明它**不长得像**「未观测到正常收尾」，且**没有**把无结局的环节逐个标成 abandoned。
    ⚠️ 这两张里的**汇总计数必须标成「截至第 N 条记录的部分计数」或直接显示为不可用**——记录都断了还给一个看起来完整的汇总，是这一档最容易犯的错。
