# graph 观测台 —— UI 页面需求文档

**给设计师** · 2026-07-26 · 配套技术方案见 `docs/DESIGN-graph-viz-2026-07-26.md`

> 读这份文档不需要任何 agent / AI 工程背景。§2 是术语表，看完就够。

---

## 0. 一句话

**一个只读的实时观测台，用来看"一批 AI 分头干活"这件事此刻进行到哪一步、每个环节喂进去了什么、吐出来了什么。**

类比：像 CI 流水线的执行页（GitHub Actions / Jenkins 那种），但每个"步骤"不是一条命令，而是**一个 AI 在读代码、写分析**；步骤之间的连线不总是明确的，有的要靠推断（见 §5）。

---

## 1. 用户、场景、要回答的问题

**唯一用户**：发起这次运行的工程师（本机打开 `localhost:7345`，无多人、无权限、无登录）。

**两个场景，权重相当**：

| 场景 | 心态 | 关键诉求 |
|---|---|---|
| **运行中盯着看**（5～60 分钟） | 焦虑、频繁瞥一眼 | 一眼看出"还在动吗、卡在哪、要不要现在打断" |
| **跑完了复盘** | 冷静、逐个点开 | 找到某个环节的输入输出，判断它干得对不对 |

**页面必须能在 3 秒内回答的五个问题**：

1. 这次跑了哪些环节？总共几个？
2. **此刻哪些在跑**、哪些已经完了、哪些挂了？
3. 环节之间是什么关系（谁在谁之后、哪些是并行的）？
4. 某个环节，**喂给它的原话**是什么？
5. 某个环节，**它吐出来的东西**长什么样？如果它被打回重做过，**两次分别**长什么样？

第 4、5 条是用户明确点名的核心，详见 §6。

## 2. 术语表

| 词 | 意思 | 设计上怎么理解 |
|---|---|---|
| **运行（run）** | 一次完整执行 | = 这个页面的全部内容，一页一个 run |
| **环节 / 节点（node）** | 一个 AI 干一件事 | 页面的基本卡片单位；有唯一 id，如 `audit-auth` |
| **引擎（agent）** | 干活的 AI 是哪家 | 五种：`codex` / `omp` / `claude` / `cursor` / `kimi`。**需要能一眼区分**，因为"换个引擎复核"是这个工具存在的理由 |
| **型号（model）/ 强度（effort）** | 同一家的不同档位 | 次要信息，详情里给 |
| **输入（input）** | 喂给这个 AI 的完整原话 | 纯文本 / Markdown，200～5000 字 |
| **产出（artifact）** | 这个 AI 吐出来的完整答案 | Markdown，**1000～50000 字**，可能含大段代码 |
| **尝试（attempt）** | 一个环节最多跑 2 次 | 第一次输出不合格会被**打回重说**一次。两次的输入输出都要能看 |
| **状态（status）** | 环节的结局 | 6 档，见 §4 |
| **依赖（deps）** | 环节之间的先后关系 | **有三种可靠性等级，必须视觉可区分**，见 §5 |

## 3. 页面结构

单页，无路由跳转，三个区域：

```
┌───────────────────────────────────────────────────────────────┐
│ A 顶栏：运行概览 + 连接状态                        （常驻，细） │
├──────────────────────────────────┬────────────────────────────┤
│                                  │                            │
│  B 主视图：环节全景               │  C 详情面板                │
│    ├ 图视图（默认）               │    点选环节后出现          │
│    └ 时间轴视图（切换）           │    未选中时收起            │
│                                  │                            │
└──────────────────────────────────┴────────────────────────────┘
```

C 区可以是右侧抽屉、也可以是全屏叠层——由你判断，但**必须能与 B 区同时可见**（用户经常要一边看图一边读某个环节的产出）。

## 4. 状态语义（最重要的视觉系统）

六档，**语义差别很大，不能只靠颜色深浅区分**：

| 状态 | 含义 | 用户看到它时该做什么 | 视觉权重 |
|---|---|---|---|
| **running** | 正在跑 | 等着；看进度 | **最高**，要有动效（唯一有动效的状态） |
| **ok** | 成功 | 点开看产出 | 低（成功是常态，不该抢注意力） |
| **contract_error** | 跑完了，但输出格式不合格 | 看它到底吐了什么 | 中 |
| **timeout** | 超时了，被打断 | 考虑加时间或拆任务 | 中 |
| **backend_failed** | 引擎明确报错 | **可以安全换个引擎重跑** | 高 |
| **unknown** | **说不清它干没干** | ⚠️ **停下来人工看，绝不能自动重跑** | **最高（与 running 并列）** |
| *reused* | 没真跑，直接复用了上次结果 | 知道这次没花钱 | 最低，**必须与 ok 区分**（否则会误以为验证过了） |

**`unknown` 的特殊性要设计出来。** 它不是"一种失败"，它是"我们不知道发生了什么"——在这套系统里它是最贵的状态，因为盲目重跑可能让同一件事做两遍。它需要一个不同于其它失败的视觉语言（不是更红，是**更"警戒"**）。

**引擎标识**：五种引擎需要稳定的视觉标记（色/字母/图形皆可），因为用户最常问的一句是"这个结论是哪家 AI 给的"。同一引擎在全页任何位置必须同一个标记。

## 5. 依赖关系的三种可靠性（本项目最特别的一点）

这套工具**故意不要求用户声明流程图**。所以环节之间的关系有三种来源，**可靠性不同，必须让用户看出来**：

| 等级 | 来源 | 可靠性 | 建议画法 |
|---|---|---|---|
| **声明的** | 用户明确写了"B 依赖 A" | 确定 | **实线箭头** |
| **推断的** | 系统发现 B 的输入里提到了 A 的产出文件 | **可能猜错、也可能漏掉** | **虚线箭头** + 可解释的提示 |
| **只有时间** | 什么都没有，只知道谁先谁后、谁和谁同时在跑 | 无因果 | **不画箭头**，退化为时间轴 |

**硬要求：实线和虚线不能长得差不多。** 把推断当事实展示，是这个页面最容易造成的误导——用户会据此判断"这个结论是基于那个结论的"，而那可能根本不成立。虚线需要一个可点击/悬浮的解释（"根据输入里出现 `nodes/audit-auth.md` 推断"）。

**因此主视图需要两个视图，可切换**：

- **图视图（默认）**：有边时画图。节点按依赖分层，同层并排。
- **时间轴视图**：横轴时间，每个环节一条泳道，长度 = 实际耗时。**当一次运行完全没有依赖信息时，自动落到这个视图**——此时图视图会退化成一堆孤立方块，没有意义。

## 6. 详情面板（用户点名的核心）

点开一个环节后要看到，**从上到下**：

### 6.1 事实条（一屏内不用滚）

环节 id · 引擎标记 · 型号 · 强度 · 状态 · 耗时 · 产出字数 · 上下文占用 · 权限档（只读/可写）

> 注：**上下文占用**在 `cursor` 和 `kimi` 两种引擎上恒为"未知"——这不是 0，设计上要能表达"未知"而不是显示成 0 或空白。

### 6.2 按尝试分段（这是"按不同轮次区分"的落点）

一个环节最多 2 次尝试。**只有 1 次时不要显示分段控件**（绝大多数情况是 1 次，不能让常态背上异常的 UI 成本）。

有 2 次时，每一段包含：

```
尝试 1  ─────────────────────────────────  ✗ 被打回
  ▸ 输入        （默认折叠，展开是完整原话）
  ▾ 产出        （默认展开，渲染后的 Markdown）
  ⚠ 打回原因    （一句话，如"缺少必需字段 verdict"）

尝试 2  ─────────────────────────────────  ✓ 采纳
  ▸ 输入        （与尝试 1 的差异值得高亮，但不是必须）
  ▾ 产出
```

### 6.3 产出的呈现（"桥输出的内容整理一下"）

原始产出是 AI 直接吐出的 Markdown，**长且杂**：可能有几千行代码块、日志粘贴、层层小标题。需要：

- **渲染 Markdown**，不是显示源码
- **超长代码块 / 日志块默认折叠**，给出"展开（约 N 行）"
- 提供 **「看原文」** 切换 —— ⚠️ **硬约束：产出文件是审计原件，页面只能渲染、绝不能改写。** 用户必须随时能看到未经处理的字节原文。
- 长内容需要**目录/锚点**或至少一个"回到顶部"

### 6.4 运行中的环节

状态为 running 时，6.2 的位置改为**实时进度**：

- 已产出字数（持续增长）
- **正在吐的文字末尾**（约 240 字的滚动尾巴）—— 这是判断"还在动 vs 卡死"最直接的证据
- 最近一条生命周期事件（如"正在执行 shell 命令"）

### 6.5 出问题时

状态非 ok 时，额外给：错误原文、诊断信息列表、"现场"文件入口（会话日志等，供深挖）。

## 7. 规模与真实数据量

| 维度 | 典型 | 极端（必须不垮） |
|---|---|---|
| 环节数 | 3～8 | **50** |
| 同时在跑 | 2～4 | 8 |
| 单个产出 | 3000～8000 字 | **50000 字** |
| 单次运行时长 | 5～30 分钟 | 2 小时 |
| 单环节时长 | 1～15 分钟 | 30 分钟 |

**50 个节点的图视图怎么办**，请给出方案（缩放 / 折叠分组 / 小地图 / 自动切时间轴，任选）。这是这个页面唯一的规模风险点。

---

## 8. 必须设计的非常态

| 情况 | 何时出现 | 需要 |
|---|---|---|
| **空态** | 页面开在脚本启动前 | "等待运行开始"，不是空白页 |
| **加载/回放** | 刚连上，正在回放历史事件 | 短暂的骨架态 |
| **断线** | 服务停了 / 脚本崩了 | 明确的"连接已断开"，**不要静默停止更新**——用户会误以为任务卡住 |
| **运行已结束** | 终态后继续看 | 顶栏明确"已结束 + 汇总计数"；页面仍完全可浏览（复盘是主要场景之一） |
| **服务自灭倒计时** | 结束后一段时间服务会自己退出 | 给提示，别让用户看着页面突然失联 |
| **零依赖信息** | 用户没声明也推断不出 | 自动切时间轴 + 一句解释，而不是显示一张空图 |

---

## 9. 明确不要做

- ❌ **任何操作按钮**——不能暂停、重跑、改参数、关环节。这是**只读观测台**，任何写操作都可能与正在跑的进程打架。
- ❌ 登录 / 权限 / 多用户 / 分享链接
- ❌ 多次运行的历史列表、跨运行对比
- ❌ 移动端适配（本机开发工具，桌面 1440 / 1920 两档即可）
- ❌ 改写或"美化"产出文本本身（只渲染，见 6.3）

## 10. 交付与参考

**交付**：桌面 1440 与 1920 两档，覆盖——① 运行中（有并行、有 running）② 已结束（含 1 个失败 1 个 unknown）③ 详情面板（单次尝试）④ 详情面板（两次尝试）⑤ 时间轴视图 ⑥ 空态/断线态。

**风格参考（同一族，请先打开看）**：本项目已有两个同类页面，新页面应与它们像是**同一套工具**：

- `skills/agent-bridge-roundtable/viz/index.html`
- `skills/agent-bridge-loop/viz/index.html`

（直接用浏览器打开即可；两者都是单文件、无需构建。）

**技术约束**（影响设计的部分）：单个 HTML 文件、零构建、零外部依赖、不能引 CDN 字体或图标库——**图标与字体请用系统字体或内联 SVG**。数据经 SSE 实时推送，页面内容会在用户眼皮底下变化，**所有区域都要考虑"内容突然出现/变化"时不跳动**。
