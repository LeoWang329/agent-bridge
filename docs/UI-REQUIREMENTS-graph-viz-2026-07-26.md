# graph 观测台 —— UI 页面需求文档

**给设计师** · 2026-07-26 · **修订 v2** 2026-07-27 · 配套技术方案见 `docs/DESIGN-graph-viz-2026-07-26.md`

> 读这份文档不需要任何 agent / AI 工程背景。§2 是术语表，看完就够。

> **v2 改了什么**：v1 假设"每个 AI 环节都是吐一段文字"。但产品在 v1 写完当天多了一种环节：**有的环节是真去改代码的**，它交付的不是文字，是**一批文件改动**。这带来一个新的状态维度、一种新的成功结局、一个必须突出的告警态，以及一种 v1 没有的"排队中"状态。改动集中在 §2、§4、§4A、§6.6、§10。

---

## 0. 一句话

**一个只读的实时观测台，用来看"一批 AI 分头干活"这件事此刻进行到哪一步、每个环节喂进去了什么、吐出来了什么、改了什么。**

类比：像 CI 流水线的执行页（GitHub Actions / Jenkins 那种），但每个"步骤"不是一条命令，而是**一个 AI 在读代码、写分析、或者真的改文件**；步骤之间的连线不总是明确的，有的要靠推断（见 §5）。

## 1. 用户、场景、要回答的问题

**唯一用户**：发起这次运行的工程师（本机打开 `localhost:7345`，无多人、无权限、无登录）。

**两个场景，权重相当**：

| 场景 | 心态 | 关键诉求 |
|---|---|---|
| **运行中盯着看**（5～60 分钟） | 焦虑、频繁瞥一眼 | 一眼看出"还在动吗、卡在哪、要不要现在打断" |
| **跑完了复盘** | 冷静、逐个点开 | 找到某个环节的输入输出，判断它干得对不对 |

**页面必须能在 3 秒内回答的六个问题**：

1. 这次跑了哪些环节？总共几个？
2. **此刻哪些在跑**、哪些**在排队**、哪些已经完了、哪些挂了？
3. 环节之间是什么关系（谁在谁之后、哪些是并行的）？
4. 某个环节，**喂给它的原话**是什么？
5. 某个环节，**它吐出来的东西**长什么样？被打回重做过的话，**两次分别**长什么样？
6. **改代码的环节，到底改了什么？改动现在在哪？**（v2 新增）

第 4、5、6 条是用户明确点名的核心，详见 §6。

## 2. 术语表

| 词 | 意思 | 设计上怎么理解 |
|---|---|---|
| **运行（run）** | 一次完整执行 | = 这个页面的全部内容，一页一个 run |
| **环节 / 节点（node）** | 一个 AI 干一件事 | 页面的基本卡片单位；有唯一 id，如 `audit-auth` |
| **引擎（agent）** | 干活的 AI 是哪家 | 五种：`codex` / `omp` / `claude` / `cursor` / `kimi`。**需要能一眼区分**，因为"换个引擎复核"是这个工具存在的理由 |
| **型号 / 强度** | 同一家的不同档位 | 次要信息，详情里给 |
| **输入（input）** | 喂给这个 AI 的完整原话 | 纯文本 / Markdown，200～5000 字 |
| **产出（artifact）** | 这个 AI 吐出来的完整答案 | Markdown，**1000～50000 字**，可能含大段代码 |
| **尝试（attempt）** | 一个环节最多跑 2 次 | 第一次输出不合格会被**打回重说**一次。两次的输入输出都要能看 |
| **状态（status）** | 环节的结局 | 6 档，见 §4 |
| **依赖（deps）** | 环节之间的先后关系 | **三种可靠性等级，必须视觉可区分**，见 §5 |
| **只读环节 / 改写环节** | 这个 AI 有没有权限改文件 | **v2 起是重要区分**，见 §4A |
| **改动结论（outcome）** | 改写环节到底交付了什么 | **v2 新增，三档**，见 §4A |
| **隔离工作区** | 改写环节各自的独立副本 | 每个改写环节在自己的目录里改，互不干扰；正常情况下改完就提交、目录删掉 |
| **分支 / diff** | 改动的最终去处 | 改写环节的**交付物**：一个分支名 + 一份改动清单 |

## 3. 页面结构

单页，无路由跳转，三个区域：

```
┌───────────────────────────────────────────────────────────────┐
│ A 顶栏：运行概览 + 连接状态                        （常驻，细） │
├──────────────────────────────────┬────────────────────────────┤
│                                  │                            │
│  B 主视图：环节全景               │  C 详情面板                │
│    ├ 图视图（默认）               │    点选环节后出现          │
│    └ 时间轴视图（切换）           │    未选中时收起            │
│                                  │                            │
└──────────────────────────────────┴────────────────────────────┘
```

C 区可以是右侧抽屉、也可以是全屏叠层——由你判断，但**必须能与 B 区同时可见**。

## 4. 状态语义（最重要的视觉系统）

### 4.1 运行阶段

| 阶段 | 含义 | 视觉 |
|---|---|---|
| **排队中（queued）** | 已经派了，但**在等名额**——同时能跑的环节数有上限（默认 4） | **v2 新增，必须有。**安静、明显是"还没开始"，不能有动效 |
| **运行中（running）** | 正在跑 | **最高权重**，要有动效（唯一有动效的状态） |
| 终态 | 见 4.2 | — |

> ⚠️ **「排队中」不能省，也不能画得像「运行中」。** 扇出 8 个环节而名额只有 4 个时，会有一半的环节处于这个状态。v1 没有它——那意味着用户会看到「8 个环节里只有 4 个」，剩下 4 个**凭空消失**，很自然地误判成"漏派了"或"卡死了"。
>
> 排队时长本身也是有用信息（"名额开太小了"），**详情里要给**。

### 4.2 结局，六档

**语义差别很大，不能只靠颜色深浅区分**：

| 状态 | 含义 | 用户看到它时该做什么 | 视觉权重 |
|---|---|---|---|
| **ok** | 成功 | 点开看产出 | 低（成功是常态，不该抢注意力） |
| **contract_error** | 跑完了，但输出格式不合格 | 看它到底吐了什么 | 中 |
| **timeout** | 超时了，被打断 | 考虑加时间或拆任务 | 中 |
| **backend_failed** | 引擎明确报错 | **可以安全换个引擎重跑** | 高 |
| **unknown** | **说不清它干没干** | ⚠️ **停下来人工看，绝不能自动重跑** | **最高** |
| *reused* | 没真跑，直接复用了上次结果 | 知道这次没花钱 | 最低，**必须与 ok 区分**（否则会误以为验证过了） |
| **abandoned** | **运行被中途掐断，这个环节没有结局** | 知道它的结果永远拿不到了 | **v2 新增**，见 §8 |

**`unknown` 的特殊性要设计出来。** 它不是"一种失败"，它是"我们不知道发生了什么"——在这套系统里它是最贵的状态，因为盲目重跑可能让同一件事做两遍。它需要一个不同于其它失败的视觉语言（**不是更红，是更"警戒"**）。

**引擎标识**：五种引擎需要稳定的视觉标记（色/字母/图形皆可），同一引擎在全页任何位置必须同一个标记。

## 4A. 改写环节：第二个状态维度（v2 新增，本次最大的改动）

有的环节被授权**真的改代码**。它跑在一个隔离的副本里，**交付物不是文字，是一批文件改动**。

所以这类环节有**两个正交的状态**，页面要表达的是**组合**，不是六档之一：

- **状态（status）**：这个 AI 跑得顺不顺（六档，同 §4.2）
- **改动结论（outcome）**：改动最后**到底落到哪儿了**（三档，下表）

### 三档改动结论

| 结论 | 含义 | 页面必须给什么 |
|---|---|---|
| **已交付** | 改动已提交，进了一个分支 | 分支名 · 改了几个文件 · 改动清单入口 |
| **无改动** | 跑完了、也成功了，但**一个字都没改** | 一句明确的"它认为不需要改动"。**没有改动清单可看——不要留一个点了没反应的入口** |
| **说不清** | 提交失败 / 检查失败 / 这个 AI 自己动了版本控制 | ⚠️ **见下，这是全页最该突出的告警** |

### ⚠️「说不清」＝ 现场被保留，必须最醒目

正常情况下改写环节跑完会**删掉自己的工作副本**。但当结论是「说不清」时，**那份副本被原样留在磁盘上**，因为里面可能有还没进分支的代码。

这时页面必须给三样东西，缺一不可：

1. **工作区的完整路径**（可一键复制——用户要去那儿看）
2. **一句话说明为什么说不清**
3. ⚠️ **一条明确警告：不要自动重跑。** 重跑可能让同一件事做两遍，或者把那份还没保住的代码覆盖掉

> 这一档在视觉上应当与「失败」区分开：失败是"这事没成"，**说不清是"这事的结果不明，而且现场还在，等你去看"**。它需要的是**行动引导**，不是错误提示。

### 三条给设计师的硬约束

1. **「无改动」不是失败。** 别把它画成灰色的、错误的、或者"什么都没发生"的样子——它是一个**正常的成功结局**（AI 判断此处无需改动，本来就可能是对的）。
2. **改动清单可能是空的，但结论仍是「已交付」。** （AI 提交了一个空提交，或者改完又改回去了。）这时分支是真的存在，只是内容没变。**别把"0 个文件"当成错误来渲染。**
3. **只读环节没有这一整个维度。** 它们恒为"不适用"——不要给只读环节留一个空的改动区块，那是噪音。

### 组合速查（决定你要出几张图）

| 状态 | 改动结论 | 页面主要在说什么 |
|---|---|---|
| ok | 已交付 | ✅ 分支 + 改动清单（**主态**） |
| ok | 无改动 | ✅ "它认为无需改动" |
| unknown | 说不清 | ⚠️ **现场保留 + 路径 + 别重跑**（**必出图**） |
| 失败三档 | 任意 | ❌ 失败信息；**若结论不是「已交付」，还要提示"改动可能只在保留的工作区里"** |

## 5. 依赖关系的三种可靠性（本项目最特别的一点）

这套工具**故意不要求用户声明流程图**。所以环节之间的关系有三种来源，**可靠性不同，必须让用户看出来**：

| 等级 | 来源 | 可靠性 | 建议画法 |
|---|---|---|---|
| **声明的** | 用户明确写了"B 依赖 A" | 确定 | **实线箭头** |
| **推断的** | 系统发现 B 的输入里提到了 A 的产出文件 | **可能猜错、也可能漏掉** | **虚线箭头** + 可解释的提示 |
| **只有时间** | 什么都没有，只知道谁先谁后、谁和谁同时在跑 | 无因果 | **不画箭头**，退化为时间轴 |

**硬要求：实线和虚线不能长得差不多。** 把推断当事实展示，是这个页面最容易造成的误导——用户会据此判断"这个结论是基于那个结论的"，而那可能根本不成立。虚线需要一个可点击/悬浮的解释（"根据输入里出现 `nodes/audit-auth.md` 推断"）。

### ⚠️ v2 新增：排队会伪造出"先后关系"

因为同时能跑的环节数有上限，**B 在 A 之后跑，很可能只是因为没名额了，跟依赖毫无关系**。

所以在**只有时间**的那一档：

- **时间轴上必须把"排队等待"和"真正在跑"画成两段**（比如浅色前导条 + 实色主体条），否则用户会把等待时间读成执行时间
- **绝对不要**把纯时间先后渲染成任何形式的箭头

**因此主视图需要两个视图，可切换**：

- **图视图（默认）**：有边时画图。节点按依赖分层，同层并排。
- **时间轴视图**：横轴时间，每个环节一条泳道。**当一次运行完全没有依赖信息时，自动落到这个视图**——此时图视图会退化成一堆孤立方块，没有意义。

## 6. 详情面板（用户点名的核心）

点开一个环节后要看到，**从上到下**：

### 6.1 事实条（一屏内不用滚）

环节 id · 引擎标记 · 型号 · 强度 · 状态 · **排队时长**（v2） · 执行耗时 · 产出字数 · 上下文占用 · **权限档（只读 / 改写）**

> 注：**上下文占用**在 `cursor` 和 `kimi` 两种引擎上恒为"未知"——这不是 0，设计上要能表达"未知"而不是显示成 0 或空白。

### 6.2 按尝试分段

一个环节最多 2 次尝试。**只有 1 次时不要显示分段控件**（绝大多数情况是 1 次，不能让常态背上异常的 UI 成本）。

有 2 次时，每一段包含：

```
尝试 1  ─────────────────────────────────  ✗ 被打回
  ▸ 输入        （默认折叠，展开是完整原话）
  ▾ 产出        （默认展开，渲染后的 Markdown）
  ⚠ 打回原因    （一句话，如"缺少必需字段 verdict"）

尝试 2  ─────────────────────────────────  ✓ 采纳
  ▸ 输入
  ▾ 产出
```

### 6.3 产出的呈现

原始产出是 AI 直接吐出的 Markdown，**长且杂**。需要：

- **渲染 Markdown**，不是显示源码
- **超长代码块 / 日志块默认折叠**，给出"展开（约 N 行）"
- 提供 **「看原文」** 切换 —— ⚠️ **硬约束：产出文件是审计原件，页面只能渲染、绝不能改写。**
- 长内容需要**目录/锚点**或至少一个"回到顶部"

### 6.4 运行中的环节

状态为运行中时，6.2 的位置改为**实时进度**：

- 已产出字数（持续增长）
- **正在吐的文字末尾**（约 240 字的滚动尾巴）—— 判断"还在动 vs 卡死"最直接的证据
- 最近一条生命周期事件（如"正在执行 shell 命令"）

### 6.5 出问题时

状态非 ok 时，额外给：错误原文、诊断信息列表、"现场"文件入口（会话日志等，供深挖）。

### 6.6 改写环节：改动区块（v2 新增）

只读环节没有这一节。改写环节按 §4A 的三档结论分别呈现：

**已交付**——需要：

- **分支名**（可复制）
- **改了哪些文件**：路径 + 增删标记（新增 / 修改 / 删除 / 重命名）的清单。典型 1～20 个文件，极端 100+，**要能滚动且不撑破布局**
- **改动详情入口**：点开看完整 diff。⚠️ diff 可能**很大**（含二进制时更大），按 §7 的超长内容策略处理
- **基线**：这份改动是基于哪个版本做的（一个短哈希即可）

**无改动**——一句话说明，**不要渲染空的文件清单或空 diff**。

**说不清**——按 §4A：路径（可复制）+ 原因 + 「不要自动重跑」警告。**这一块的视觉权重应当高于同页任何其它内容。**

## 7. 规模与真实数据量

| 维度 | 典型 | 极端（必须不垮） |
|---|---|---|
| 环节数 | 3～8 | **50** |
| 同时在跑 | 2～4（**受名额上限约束，默认 4**） | 8 |
| **同时排队** | 0 | **46**（50 个环节、4 个名额） |
| 单个产出 | 3000～8000 字 | **50000 字** |
| **改动文件数** | 1～20 | **100+** |
| 单次运行时长 | 5～30 分钟 | 2 小时 |
| 单环节时长 | 1～15 分钟 | 30 分钟 |

**50 个节点的图视图怎么办**，请给出方案（缩放 / 折叠分组 / 小地图 / 自动切时间轴，任选）。这是这个页面唯一的规模风险点。

> v2 补充：**46 个环节同时排队**是真实可能的形态。列表按 §4 排序时，一大片"排队中"卡片不该淹没掉那 4 个真正在跑的——**排队区可以折叠成一行摘要**（"另有 46 个排队中"）。

## 8. 必须设计的非常态

| 情况 | 何时出现 | 需要 |
|---|---|---|
| **空态** | 页面开在脚本启动前 | "等待运行开始"，不是空白页 |
| **加载/回放** | 刚连上，正在回放历史事件 | 短暂的骨架态 |
| **断线** | 服务停了 | 明确的"连接已断开"，**不要静默停止更新** |
| **运行已结束** | 正常收场 | 顶栏明确"已结束 + 汇总计数"；页面仍完全可浏览 |
| **⚠️ 运行被中途掐断** | **用户按了 Ctrl-C / 进程被杀** | **v2 新增，且这是常见情况不是边缘情况**——见下 |
| **服务自灭倒计时** | 结束后一段时间服务会自己退出 | 给提示，别让用户看着页面突然失联 |
| **零依赖信息** | 用户没声明也推断不出 | 自动切时间轴 + 一句解释 |

### ⚠️「运行被中途掐断」为什么必须单独设计

技术上有个事实：脚本被强行终止时，**它来不及写下"我结束了"这条记录**。页面如果傻等那条记录，就会**永远显示"运行中"**——而运行早就没了。

所以页面会自己发现"写日志的那个进程已经不在了"，此时必须：

1. 顶栏明确「**运行已中断（未正常收场）**」——与「已结束」**是两回事**，不能混用同一个视觉
2. 把还停在**排队中 / 运行中**的环节，统一改成 **`abandoned`（没有结局）**，别让它们永远转圈
3. 说清楚这些环节的结果**永远拿不到了**——不是"还在跑"，也不是"失败了"

> 这条对复盘场景尤其重要：用户跑完（或掐断）之后才来看页面是**常态**，页面此时的第一印象必须是准确的。

## 9. 交互清单

**必须有**：选中环节（B↔C 联动）· 展开/收起（输入、产出、改动清单）· **复制**（输入原文、产出原文、分支名、工作区路径）· 「看原文」切换 · 实时更新 · 视图切换（图 ↔ 时间轴）· 排队区折叠。

**明确不要做**：

- ❌ **任何操作按钮**——不能暂停、重跑、改参数、关环节，**也不能合并分支**。这是**只读观测台**，任何写操作都可能与正在跑的进程打架。
- ❌ 登录 / 权限 / 多用户 / 分享链接
