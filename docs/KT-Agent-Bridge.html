Agent Bridge 使用场景 KT

从使用者视角理解：什么时候该用、该怎么说、过程如何推进、最终会得到什么

项目资料：https://research.ic-digital.cn/p/9pX90z1-Zuw2kq6ZTomK-Q

核心理解：Agent Bridge 不是另一个聊天窗口，而是一套“让当前 Agent 调度其他独立 Agent”的能力。 使用者不需要操作底层会话工具，只要明确说出要使用 Agent Bridge、希望完成的任务、是否允许改文件，以及是否需要独立复核、并行调查、圆桌讨论或无人值守闭环。

先选场景

你的诉求应使用的场景典型结果
找一个独立 Agent 给第二意见、复核材料或并行查资料基础委托一份独立结论或多份并行结果
实现功能、评审代码、设计方案或定位复杂 Bug开发工作流 Dev实现、独立评审、修复和验证闭环
至少需要三个不同视角，对高风险问题作裁决或全面探索圆桌 Roundtable匿名多轮审议记录和主席综合结论
任务很大，希望从需求合同一直自动跑到黑盒验收通过自动交付 Loop验收合同、逐 Goal 迭代证据、整支评审和交付报告
不要滥用：普通问答、小修小补、路径明确且当前 Agent 自己就能完成的任务，不需要 Agent Bridge。只有明确需要“其他独立 Agent”带来的复核、并行、角色分工或闭环价值时才使用。

场景一：基础委托

Agent Bridge
独立第二意见只读调查并行多开持续追问

什么时候用

  • 你希望另一个模型独立复核当前结论，避免“自己评自己”。
  • 一个问题可以拆成多个互不依赖的方向，希望同时调查。
  • 你指定要用 OMP、Codex、Claude，或经 OMP 调用某个模型。
  • 任务需要连续追问，希望同一个委托 Agent 保留这条任务线的上下文。

你需要怎么说

必须明确说出“使用 Agent Bridge”或“找其他独立 Agent”。建议同时给出任务范围、工作目录、是否允许改文件和完成标准。

使用 Agent Bridge，找一个独立 Agent 只读检查这个项目的鉴权逻辑。
重点看登录绕过和权限提升，不要修改文件。最终按严重程度列问题，并给出文件位置和证据。
使用 Agent Bridge 并行找两个不同 Agent：
一个检查性能瓶颈，一个检查异常处理。两边都只读，最后汇总共同问题和分歧。

实际会怎么运行

创建独立会话 → 发出任务 → 后台执行 → 分段查看进度 → 读取完整结果 → 必要时追问 → 结束会话
  • 长任务不会因为一次等待结束而中断，主 Agent 会用短周期持续查看进度。
  • 并行任务会开启多个独立会话，先完成的结果可以先处理。
  • 同一任务的追问会继续使用原会话；换模型或换无关任务时会创建新会话。
  • 只读任务默认允许读取文件、搜索和执行调查命令；只有明确要求修改时才使用写权限。

你最终会拿到什么

主 Agent 会整合委托结果，并对关键结论自行复核。若委托 Agent 修改了文件，主 Agent仍会检查差异并执行必要测试，不会直接把委托方的“已完成”当作事实。

场景二：开发工作流

Agent Bridge Dev

Dev 适合开发类任务。它不是简单“找一个 Agent 写代码”，而是根据任务选择实现者、评审者、架构师或调试者，并组织成闭环。

2.1 已明确需求：实现 → 独立评审 → 修复 → 复评

适用：功能目标和验收标准已经明确，希望由委托 Agent 实现，并由另一个不同引擎或模型独立评审。

使用 agent-bridge-dev 实现“导出 CSV”功能。
需求以 docs/export-spec.md 为准；只允许修改 src/export 和对应测试。
完成后必须找一个不同引擎的 reviewer 独立评审，修到 APPROVE，再由你运行必要测试并汇报。
实现者写代码和测试 → 独立 Reviewer 检查固定范围 → 有问题退回实现者 → 重新评审 → 主 Agent 自查

Reviewer 必须与实现者使用不同引擎或模型。评审范围会先固定，避免一边评审一边继续变化导致结论失效。

2.2 方案未定：双架构师多轮讨论

适用：存在两条以上合理路径，且涉及数据模型、公共 API、并发模型、框架选型或跨模块契约等高风险决定。

使用 agent-bridge-dev 做架构设计讨论。
问题是任务调度应该采用数据库队列还是消息队列。
请先说明准备拉哪些独立架构师和讨论轮数，等我确认后再开始；最后给出推荐方案、权衡和未决点，不要写代码。
用户确认阵容 → 两个异引擎架构师独立出方案 → 交叉讨论 2–3 轮 → 主 Agent 综合 → 用户确认后才进入实现

路径唯一、改动局部或很容易回退时，应跳过架构讨论，直接进入实现。

2.3 复杂 Bug：双调试者并行定位根因

适用：问题难复现、根因不清、单一路径容易形成先入为主判断。

使用 agent-bridge-dev 调试这个偶发超时问题。
复现步骤、日志和最近改动在 docs/timeout-case.md。
请让两个不同引擎的 debugger 并行只读调查，先比较根因；根因确认后只允许一个 writer 修复，并走独立评审。
主 Agent 固化现场 → 两个调试者并行只读调查 → 比对一致点与分歧 → 单一 Writer 修复 → 独立复审

调查阶段不允许两个 Agent 同时写同一工作区。需要诊断埋点时，由主 Agent统一加入一次，再把结果反馈给相关调试者。

场景三：多 Agent 圆桌审议

Agent Bridge Roundtable
默认 3 席匿名盲发多轮收敛可选实时可视化

什么时候值得开圆桌

问题必须确实需要三个以上不同视角，且选错代价高、决策难回退，或者漏掉关键维度的代价很高。普通方案二审只需要两个架构师时，使用 Dev 即可。

先选一种模式

模式适用问题目标示例
裁决 adjudicate“哪个好、能不能、该不该”防止假共识导致选错，在互斥路径中作出决定该选自研权限系统还是接入统一 IAM？
探索 explore“有哪些、怎样全面、把问题想透”防止漏点，把互补视角铺全并继续深挖全面梳理 Agent 平台上线前的风险和治理方案

你需要怎么说

使用 agent-bridge-roundtable，开一场 3 席裁决圆桌。
议题：内部知识库应该采用方案 A 还是方案 B。
重点从安全、运维成本和长期扩展性审议；遇到没有客观优劣的产品取舍时停下来问我。
我希望打开实时可视化。
使用 agent-bridge-roundtable 的探索模式，全面深挖“医疗问答系统上线需要考虑哪些风险”。
至少覆盖合规、数据、模型质量、监控和人工升级机制，最终输出分层清单和建议路线图。

实际会怎么运行

确定模式和席位 → Round 0 各席互不可见地独立作答 → 匿名共享完整论证 → 多轮交锋或延伸 → 主席判断收敛 → 输出终稿
  • 各席使用不同引擎或模型，第一轮盲发，避免相互锚定。
  • 后续轮次可以看到其他席的完整论证，但看不到发言者身份；不是只看主席摘要。
  • 主 Agent 是主席，只负责调度、记录、判断是否收敛和写最终综合，不下场代表某个立场。
  • 涉及成本与速度、产品优先级、不可逆安全姿态等只能由人决定的问题，会暂停并请用户拍板。
  • 用户同意时可开启实时页面查看轮次、发言和收敛进度；无论是否开启，可审计记录都会保留。

你最终会拿到什么

一份主席综合终稿，以及完整的匿名轮次记录、分歧与覆盖记录。圆桌产出的方案若需要落地写代码，后续仍应进入 Dev 的实现与独立评审流程。

场景四：合同驱动的自动交付循环

Agent Bridge Loop
验收合同生成者 × 验证者黑盒验收支持无人值守

什么时候用

  • 任务较大，不能接受“一轮实现后口头说完成”，希望每个目标都有可执行验收标准。
  • 希望生成者与验证者严格分离，由不同引擎互相制衡。
  • 需要连续多轮修复直到全绿，并保留全过程证据。
  • 需要无人值守或定时触发，在独立工作区完成后交付分支和报告。

你需要先给出的两个选择

  1. 人在环还是无人值守：人在环时，关键歧义和卡点会询问你；无人值守时不提问，由主 Agent 作合理假设并写入假设账本。
  2. 是否使用评审团：可选双架构师、N 席圆桌或不使用。无人值守时强制使用评审团，默认双架构师。

请求示例：人在环

使用 agent-bridge-loop，人在环，评审团使用双架构师。
任务：为现有服务增加批量导入功能。
先和我确认需求并生成验收合同；合同经我确认后再开始实现。每个 Goal 必须经过独立黑盒验证，最后做整支代码评审。

请求示例：无人值守

使用 agent-bridge-loop，无人值守，评审团=架构师。
任务：修复 docs/issue-142.md 描述的问题并补齐回归测试。
在独立 worktree 和分支中完成；歧义自行拍板并记入假设账本。全部验收通过后交付分支名、证据和最终报告。

实际会怎么运行

需求挖掘 → 验收合同 → 用户/评审团过闸 → 生成者实现 → 独立验证者黑盒验收 → 缺陷退回循环 → 整支评审 → 最终报告
  1. 需求合同：把任务拆成多个 Goal，每个 Goal 写明可执行的验收标准、边界和验证环境。
  2. 生成：生成者按当前 Goal 实现并编写产品测试。
  3. 验证：另一个引擎的验证者从公开边界执行测试、端到端探针或日志检查；生成者不能自证通过。
  4. 循环：有任何失败就把缺陷原样退回生成者修复，随后使用 fresh 验证者全量重验。
  5. 收官：全部 Goal 通过后，再做一次覆盖整支改动的独立代码评审和主 Agent 自查。

如何理解“通过”

  • 生成者说“完成”不算通过，只有独立验证者对当前 Goal 给出全绿证据才算。
  • 有用户可观察行为的 Goal，不能只跑生成者自己写的单元测试，还需要独立的端到端、CLI、API、文件或日志验证。
  • 概率性或 LLM 输出不能单次等值判断，要在合同中约定采样次数、通过配额和判断规则。
  • 如果达到迭代上限仍未通过：人在环会让用户选择加轮、修改合同或放弃；无人值守会停止后续 Goal，并在报告中标红。

你最终会拿到什么

验收合同、假设账本、每个 Goal 每轮的生成与验证记录、验证资产、整支评审结论和最终交付报告。无人值守模式还会给出独立分支名，不会直接占用或污染用户正在工作的主树。

权限与交互怎么表达

你的意图建议在请求里明确写
只分析，不改文件“只读调查，不要修改文件；允许运行测试和诊断命令。”
允许实现“允许修改文件；只能改这些路径：……；完成标准：……”
要求真正独立复核“Reviewer 必须与实现者使用不同引擎或模型，并新开独立会话。”
需要并行“按互不重叠的子任务并行；多个写任务不得修改同一批文件。”
希望持续知晓进度“任务运行期间定期汇报当前阶段、部分输出和是否仍在推进。”
希望完全自动完成“使用 Loop，无人值守；歧义自行拍板并记录，卡死按 halt 处理。”

常见选择错误

  • 错误：一个小改动也开 Loop。
    正确：需求明确的单任务实现和评审使用 Dev。
  • 错误：只需要两个方案意见却开 N 席圆桌。
    正确：使用 Dev 的双架构师讨论。
  • 错误：让实现者用同一会话评审自己。
    正确：使用不同引擎或模型的新 Reviewer 会话。
  • 错误：两个写 Agent 并行修改同一批文件。
    正确：拆成不重叠范围、使用隔离工作区，或改为串行。
  • 错误：把“单元测试绿”当成 Loop 的完整验收。
    正确：从用户可观察边界增加独立黑盒验证。
最简单的使用口诀：只要第二意见，用基础委托；要做开发闭环，用 Dev；要三个以上视角审议，用 Roundtable；要从验收合同自动跑到全绿，用 Loop。
